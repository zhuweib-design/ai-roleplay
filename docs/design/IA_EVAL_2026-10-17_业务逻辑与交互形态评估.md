## 0. 结论先行

**推荐：两级互换单屏流（方案二）作为手机端主轴交互形态**——"使用"页（单聊/群聊/阅读）满屏占主体，列表与详情两级互换、同一时刻只存在一级，配置与编辑收进二级页与底部抽屉；桌面四栏并置不动。

一句话理由：**这个应用里已经做过一次自然实验**。单聊页就是这个形态（页头 56 + 消息区 593 = 70% + 输入 73），它是全项目体验最好的页面、键盘行为正常、被评审列为"唯一不需要组成层改造的页面"；群聊、世界书、设置**不是**这个形态，它们贡献了四项 P0 中的**三项**（消息区 32px、设置 4/7 可达、键盘溢出 233px）。

**第四项不在形态账上，必须写在这里而不是藏起来**：焦点双向逃逸（P0-4）实测发生在 `/chat`——也就是被当作正面范本的单聊页（评审 §2.3：390×844、连按 12 次 Tab 有 11 次落在离屏抽屉）。它是 `inert` 接线方向反了（`ChatView.vue:89/92/95`），与页面组成无关。**所以正确的表述是：形态能解决"空间分配"，解决不了"接线纪律"**——前者靠方案二，后者靠批次 0-6 单独守，两者不能互相顶替。承认这条反例后，剩下三项 P0 仍全部落在形态账上，结论不变（详见 §5.2 理由链 1）。

四个候选的排序：**方案二 > 方案三**（其抽屉治理作为方案二的子集保留）**> 方案一**（已被实测否定）**> 方案四**（与创作业务冲突，不取）。依据见 §4 打分与 §5 理由链。

## 1. 底层业务逻辑与核心功能模块

### 1.1 系统本质：一条带缓存纪律的提示词流水线

抛开 UI，这个产品的核心是一条**生成流水线**。读 `src/core` 各模块头部注释，链路如下：

| 环节 | 模块 | 职责 | 关键纪律 |
|---|---|---|---|
| L0 上下文结构层 | `l0-l2-runtime.ts` | 字节稳定的 standing 常驻前缀 → 前缀缓存命中；会话级情绪状态机（独立于角色卡，规则标注） | 注入**绝不触碰 standing 前缀**，否则缓存全失 |
| 世界书激活 | `lorebook-scanner.ts` | 扫描最近 N 条消息，按关键词/常量/概率策略激活条目；AND ANY/ALL、NOT ANY/ALL 逻辑；包含组同组只插一条 | 激活结果进上下文的动态段 |
| 宏替换 | `macro.ts` | `{{char}}`、`{{getvar::x}}`、`{{setvar::x::v}}`；`{{user}}` 按原文保留（世界内用户资料由世界书单独注入） | 纯文本变换，无副作用 |
| 向量检索注入 | `dual-channel-runtime.ts` | 双通道 RAG：记忆/情绪进 `ragContext`（动态段，user turn 侧）；时间衰减防语气僵硬 | 默认关；**fail-open**——模型未装/嵌入失败一律返回 `''`，不阻断主链路 |
| 生成 | `chat-generation` / `local-model-engine` / 各 provider | 云端 API 与本地 WebLLM 双通道 | — |
| L2 输出纪律层 | `l0-l2-runtime.ts` | 状态性旁白精简（protect → compressMetaNarration → restore）；Auto-Clarity 软回退声明追加到系统提示词 | 只动输出，不动输入 |
| 旁白解析 | `narration.ts` | 模型在同一条回复里用成对符号 `⟦⟧` 夹出心理段，顺序：对白 → 心理 → 对白 | 规则文本面向模型，非 UI 文案 |
| 痕迹登记 | `event-trace.ts` / `promptTrace` | 随机事件注入痕迹：**只留标识，不留正文** | 界面回答"这轮带进了哪条事件"，一句名字加一个去处 |

三个设计基因贯穿全链，它们直接约束交互形态：

1. **缓存纪律**——"动态的绝不进前缀"。这决定了上下文面板、就绪条这类"状态展示"必须是**读**的表面，不能反过来诱导用户在会话中频繁改配置（改一次 = 前缀作废一次）。
2. **fail-open**——辅助系统（RAG/嵌入/情绪）坏了就静默降级，主对话永远能跑。UI 侧的对应物是：辅助能力的状态要**可见**（否则用户不知道它没生效），但**不可打扰**。就绪条的存在就是为此。
3. **状态诚实**——见 §1.4。

### 1.2 业务域 → 模块 → 页面，及每页的"本质"

20 个 store、91 个 core 模块、16 个视图，归成八个域：

| 业务域 | 代表模块（store / core） | 视图 | 页面本质 |
|---|---|---|---|
| 对话 | chat / chat-session / chat-generation / chat-runtime / chat-context / chat-memory / group-chat / chat-group-runtime | ChatView、GroupChatView | **使用** |
| 角色 | character / character-version / character-card / character-generator / character-version-control | CharactersView、CharacterEditorView、CharacterVersionView | **创作**（列表页是使用） |
| 世界观 | lorebook / lorebook-scanner | WorldBookView | **创作** |
| 故事引擎 | story / events / random-events | StoryEngineView、RandomEventsView | **创作/配置** |
| 能力 | local-model / embedding / user-vector-model / image-generation / data-bank | LocalModelView、ImageGeneratorView、DataBankView | **配置 + 使用**（生成动作是使用） |
| 社区 | community-market / market-index | CommunityMarketView | **使用**（浏览获取；登录为本地模拟，`community-market.ts:288-300` 的 `login(name)` 不收凭据无后端） |
| 系统 | settings / api-key-crypto / backup / audit-log / guided-tasks | SettingsView、GuideView | **配置 + 元页面** |
| 归档 | data-bank / character-version | ArchivesView | **使用**（查看） |

"页面本质"这一列是全文的支点：**使用页要求内容份额最大化，创作页要求工具密度，配置页要求可达与低频收敛**。三种本质要求三种组成形态，任何"一套形态通吃"的方案（现状即如此）都会同时做坏三种页面——现状正是通吃的代价。

### 1.3 导航：单一来源与四种表面

`nav-model.ts` 是导航唯一真源（已核实：`src/` 内 `matchMedia` 命中 6 处，其中**实际调用仅 2 处**（`viewport.ts:36/37`），其余 4 处是注释提及；6 处全部落在 `viewport.ts` 内。导航入口全部在 nav-model 声明）。4 组（conversation / creation / capability / archive），17 条路由，驱动四种表面：桌面 rail（112px，≤900px 收 64px）、移动底部 Tab（当前 6 个）、聚合页 MoreView、ChatView 左右抽屉。

派生机制本身是对的（一处声明、四处消费），但清单有三处结构性缺口：

- **guide 是移动端孤儿**：`nav-model.ts:219-220` 的 guide 项 `mobileTab: false` **且** `inMore: false`——手机新用户既不占 Tab 也不在「更多」里，任务中心只能靠记住 URL 撞进去。
- **8/12 内容入口只能从「更多」进**，聚合页成了杂物抽屉。
- **`DETAIL_ROUTES`（`mobile-nav.ts:21-31`）让 8 个视图进页面就摘掉底部导航**（9 条路由，其中 `character-edit` 与 `character-new` 是同一个编辑器，去重后 8 个视图），其中多数不是沉浸式编辑器。

### 1.4 设计基因：状态诚实

这个项目在"界面不得谎报状态"上有成体系的投入，这在同类项目里少见，也是交互形态必须保护的东西：

| 模块 | 机制 |
|---|---|
| `readiness.ts` | 就绪状态唯一判定源：模型/世界书/文档检索/语音的依赖只此一处判断，就绪条、前置横幅、关联面板**只能读它**，杜绝"面板说没配、toast 说配了、按钮却禁用" |
| `guided-tasks.ts` | 任务式分步引导：完成与否**读真实数据**（store/消息/开关），删掉角色任务自动退回未完成，导入备份自动勾选——"界面永远不会宣称一件没有发生的事" |
| `event-trace.ts` / `promptTrace` | 注入痕迹只留标识不留正文 |

推论：**交互形态必须给"状态诚实"一个常驻的展示位**（就绪条），而不是把它收进弹层——收进弹层等于鼓励用户不看状态就发消息，然后对着失败结果猜原因。方案二保留单行就绪条（0-4），与此基因一致。

### 1.5 数据与安全底线（约束配置页形态）

`api-key-crypto.ts`（PBKDF2 600k + AES-GCM，主密码仅运行时内存）、`src/services/backup-service.ts:48`（`exportAll` 检测明文 API Key 拒绝导出并记审计日志；注：`src/core/backup.ts` 只有类型与 `validateBackup`，不含导出逻辑）。推论：**含主密码的「安全」分类在手机上物理不可达**（实测 4/7 可达）不是体验瑕疵，是安全功能在移动端的缺席。

## 4. 交互形态方案评估

### 4.1 评估判据（5 条，量化口径由主理人校准）

| # | 判据 | 口径 |
|---|---|---|
| J1 | 内容份额 | 使用页 390×844 下内容区向单聊基准（70%）靠拢，组成层方案实测 43% 为过渡值；**硬门槛：键盘弹起（视口 500 高）输入条必须在视口内** |
| J2 | 退出完备 | Android 返回键三态语义（关层 → 回一级 → 默认）；每屏有说出去向的返回；底部导航全程在场（摘除须有明确理由） |
| J3 | 形态-业务匹配 | 区分"使用/创作/配置"三种本质并分别给形态，而非一套通吃 |
| J4 | 资产保护 | 零新增颜色；9 套皮肤 × 26 组对比度门禁与 67 处存量读数不变；桌面四栏不动 |
| J5 | 信息架构完备 | 无孤儿入口（guide）、无「更多」黑洞化；内容入口 ≤2 步且双端一致 |

### 4.2 四个候选形态

**方案一 · 现状修补**：维持"桌面双栏直塞手机"，对每处缺陷打点（min-height、z-index、逐页调优）。
**方案二 · 两级互换单屏流**（`.m-swap`，原语定义见方案文档 §3.3.1）：使用页满屏；"列表 + 详情"页面在手机上两级互换、同一时刻只存在一级，靠一条 history 记录切换（系统返回即回列表）；配置与编辑收进二级页自己的入口与底部抽屉；桌面四栏不动。
**方案三 · 抽屉主导**：保持现有页面组成，导航与配置全走抽屉（SillyTavern/Mobilyze 路线）。
**方案四 · 沉浸优先**：聊天即应用——对话满屏，其余一切（角色/世界书/设置）降为弹层与极简入口（Character.AI 路线）。

### 4.3 打分与结论

| 判据 | 一 现状修补 | 二 两级互换 | 三 抽屉主导 | 四 沉浸优先 |
|---|:---:|:---:|:---:|:---:|
| J1 内容份额 | **✗** 补丁两版实测皆错（`min-height:40vh` 在 844 与 500 双档均把输入条挤出视口，评审 §2 的 A/B 对打表） | **✓** B2 实测 43% 且 500 高输入条 456 ≤ 500（评审 §7 P0-1） | **△** 抽屉关着时消息区仍是残值；开着时配置全屏遮内容——份额问题没解决 | **✓** 聊天满屏，份额最大 |
| J2 退出完备 | **△** 返回键仍无处理，补丁清单越来越长 | **✓** 两级互换 + pushState 天然获得系统返回语义（方案 1-1、2-3） | **✗** 抽屉状态机已被实测证明不可靠（inert 方向反、12 Tab 11 落离屏）；先修状态机才配谈主导 | **△** 弹层堆叠的返回语义更难做对 |
| J3 形态-业务匹配 | **✗** 一套形态通吃，正是病灶 | **✓** 使用页满屏 / 创作页两级降级 / 配置页全屏单列，三分与 §1.2 的页面本质一一对应 | **△** 仍是"每页自己想办法" | **✗** 创作域（角色/世界书/数据银行）是核心业务，全弹层化等于废掉创作 |

## 5. 推荐结论与理由

### 5.1 推荐

**以方案二（两级互换单屏流）为手机端主轴形态实施**，方案三不做独立方案、其抽屉治理全部并入方案二（`inert` 修复 = 批次 0-6；群配置收抽屉 = 批次 1-2 的「群设置」抽屉）；方案一与方案四不取。实施载体即方案文档批次 0–4，本文不重复排期。

### 5.2 理由链

1. **证据一致性（最硬的一条，含必须承认的反例）**：单聊页（已是方案二形态）= 70% 内容份额、键盘正常、评审确认"唯一不需要组成层改造"；群聊/世界书/设置（不是该形态）= 四项 P0 中的三项。同一应用、同一套皮肤、同一作者，唯一自变量是页面组成。

   **反例**：第四项 P0（焦点双向逃逸）实测发生在 `/chat`——被当作范本的单聊页。它是 `inert` 接线方向错误，与页面组成无关。**这条反例改变的是论证的边界，不是结论**：形态决定的是"空间怎么分"，而"接线纪律"（inert/焦点/返回语义）是独立的第二层，必须单独守（批次 0-6）。若把四项 P0 全算进形态账，这条理由会被一句话问倒；分开算，剩下的三项仍全部落在形态上，结论依然成立。
2. **业务匹配**：§1.2 的"使用/创作/配置"三分直接映射为方案二的三种组成——使用页满屏、创作页两级降级（列表与阅读全功能、重编辑引导回桌面）、配置页全屏单列。方案一与方案三对三种本质给同一个形态，方案四把创作本质废掉。
3. **与系统基因相容**：缓存纪律要求配置"改得少、看得见"——两级互换把配置移出常驻区但保留二级页入口与单行就绪条；状态诚实要求就绪状态常驻可见——方案保留就绪条（0-4）而不是收进弹层。fail-open 的静默降级恰好需要就绪条这种"不打扰的可见"来对冲。
4. **资产保护**：组成层零新增颜色，9 套皮肤 × 26 组对比度门禁读数不变，回归面收缩到布局。方案四则要重写 nav-model 的四种表面，等于把最值钱的资产（视觉系统 + 导航单一来源）重新冒一次险。
5. **成本与风险**：方案二已有可执行的批次（0 当天可完成 → 1 组成层 → 2 导航 → 3 触摸 → 4 存量债），每项带可自动化判据；最贵的未知数（`.m-swap` 与 vue-router 的分工）已有约束（不新增路由，一层 `pushState`）。方案四的成本是"整个导航模型"，收益却与方案二在 J1 上打平。

### 5.3 本轮新增的两件事（已登记进方案文档批次 2）

| 编号 | 事项 | 修法建议 | 判据 |
|---|---|---|---|
| 2-6 | **guide 移动端入口**（T3）：`nav-model.ts:219-220` 的 `inMore: false` → `true`，让任务中心进「更多」聚合页；不改 `mobileTab`（首屏 Tab 不给引导，理由与"新用户第一件事是配模型，设置保留"一致——引导是二次入口不是一级入口） | 一行数据改动 + 「更多」聚合页卡片描述（nav-model 已有 descKey 机制） | 手机新用户 ≤3 步到达任务中心（Tab → 更多 → 引导卡） |
| 2-7 | **市场"账号"叙事降级**（T7）：登录为本地模拟（`login(name)` 无后端），交互不应给出账号预期——聚合页/市场页的文案与入口描述按"导入工具"表述，不出现"登录/账号"承诺 | 文案层改动，无逻辑改动 | 市场相关界面无"登录/账号"表述；i18n 门禁通过 |

两条都是小改动，放批次 2（导航与形态）与既有条目同批验收。

### 5.4 不做什么

- **不动桌面四栏**——画像 D 的 D1 场景是产品的创作根基，四栏并置本身是价值（评审 §8 同结论）。
- **不给内容设 vh 下限**——方案一思路的残余，评审已用 A/B 对打实测否定两版。
- **不做方案四**——除非产品定位转向"纯对话消费、创作全砍"，目前业务不支持。
- **不先谈抽屉主导**——抽屉状态机（inert/焦点/返回语义）在修复完成前没有资格承载主导导航；修复完成后它也只是方案二里的"配置承载件"。
