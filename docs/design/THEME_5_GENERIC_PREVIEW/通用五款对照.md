# 通用五款配色 · 真实页面对照（2026-10-12）

结论先说：

- **C 新终端**：真实页面上零处不达标，可直接落地。
- **A 极光夜曲、B 墨纸**：各只有 1 类问题（主按钮/次按钮的文字色），改成该套自己已有的另一个色就过线，实测数字在下面。
- **E 新粗野**：10 处，但全部可修，规则很简单——它的亮粉 `#FF5C8A` 只能做色块与边框，不能做 13px 文字，也不能做"承载白字的底"。
- **D 樱雾玻璃**：13 处，其中有一类**修不掉**：它的辅色紫 `#8B7CF6` 作为承载文字的面时，配白字 3.33、配深字 4.29，两个都不到 4.5。这套要落地，需要设计师补一个更深的紫变体，不是我这边能靠换文字色绕过的。

这一版不是在原型页面里看的，是**注入到真实产品页面**后量的：产品自己的 DOM、组件、字号与层级。

复现（需 dev server 在跑，本项目 e2e 端口 5179）：

```
BASE_URL=http://localhost:5179 OUT_DIR="$PWD/docs/design/THEME_5_GENERIC_PREVIEW" SKINS=base,a,b,c,d,e node scripts/skin-preview.mjs
```

| 款 | 底色 | 主色 | 形状语言 | 不达标文本 | 渐变底需人工看 | 判断 |

"不达标文本"= 真实 DOM 里**纯色底**文本，按 WCAG AA 逐元素算（正文 4.5:1；≥24px 或 ≥18.66px 粗体按 3:1），四条路由合计。渐变底与图片底（头像、主按钮）算不出纯色对比，单独计数交给人看截图，与产品里 `Avatar.vue` 的注释同一口径（"axe 无法计算渐变"）。

### A 极光夜曲：3 处，一类

| 实测 | 需要 | 位置 | 配对 |
|---|---|---|---|
| 3.33 | 4.5 | 「新建」「创建新世界书」等主按钮（13px） | 白字 `#FFFFFF` 压在 accent `#8B7CF6` 上 |

改法（用该套自己已有的色）：按钮文字改深墨 `#0A0B14`（该套 `--color-text-inverse`）压在 `#8B7CF6` 上 = **5.89** 过线。
注意另一条路不通：把主色压暗成该套的 `--color-accent-active` `#7867E8` 再配白字只有 **4.28**，仍差；配深字是 4.58 勉强过，但会牺牲极光紫的明亮感。

### B 墨纸：1 处

| 实测 | 需要 | 位置 | 配对 |
|---|---|---|---|
| 4.41 | 4.5 | 「AI 生成」按钮文字（13px） | 纸白 `#FAF8F3` 压在 warning `#9A6B12` 上 |

改法：同一处文字换成纯白 `#FFFFFF`（该套 `--color-warning-contrast` 就是白）= **4.68** 过线。差的就是那一点纸色。

### C 新终端：0 处

纯色底全部达标。这套的按钮文字本来就是深墨（`#03130F` 压在 `#38F2C8` 上 = 13.32），是五款里唯一"亮主色配深字"的，所以天然过 AA。

### D 樱雾玻璃：13 处，其中 5 处是设计缺口

| 实测 | 处数 | 位置 | 配对 | 能不能修 |
|---|---|---|---|---|
| 2.54 | 1 | 次按钮文字 | 白字压在 warning `#E0912B` | 能：改深墨 `#2C2740` = **5.61** |
| 3.03 | 5 | 导航激活项文字、「创建第一个世界书」 | 该套背景色 `#F6F3FB` 当文字压在 `#8B7CF6` 上 | 见下：换白字也只 3.33，换深字 4.29 |
| 3.03–3.33 | 7 | 「正在生成…」、世界书引导按钮、页签文字与计数 | 辅色紫 `#8B7CF6` 作小字（浅底上）／白字压在紫底上 | **不能靠换文字色解决** |

关键点：`#8B7CF6` 这颗紫在"承载文字"这件事上两头都不达标（白字 3.33、深字 4.29）。要么它只用于边框/色块不承载文字，要么设计师补一个深色变体（例如把 `--color-accent-2` 拆成 `-2` 与 `-2-ink`，后者压到 `#5B4BC0` 量级）。这不是映射问题，是这套配色的真实缺口。

## 3. 落地前必须先修的三处耦合（不修就换不全）

| 问题 | 证据 | 后果 |
|---|---|---|
| 组件直接引用调色板色阶，不经过语义层 | 45 行、48 处 `var(--tk-*)`：`--tk-cyan-500/600/700`（25 处，含头像渐变两端）、`--tk-red-500/600/700`（21 处）、`--tk-yellow-500`、`--tk-green-500` | 换皮肤时头像渐变与部分强调色**不跟着变**；本轮"渐变底待人工看"的 4 处就是这个 |
| 死引用兜底：`src/styles/layout.css:79` 的 `color: var(--primary-foreground, var(--background))` | `--primary-foreground` 全仓无定义（M18 体检 B 类里它出现 9 次） | 深色皮肤侥幸能读，浅色皮肤必然糊（D 的 5 处、E 的 5 处就是它） |
| 遮罩写死：`.modal-overlay` 是 `rgba(0, 0, 0, 0.65)` | 探针在四条路由上读到的都是这个值 | 原型每套自带 `--color-bg-scrim`（B 是 `rgba(28,26,23,.42)`），不接进来则浅色皮肤的弹窗发脏 |

这三处都属于 M18 报告里"迁移会顺带显形的历史问题"，不是新皮肤带来的 bug，但**换配色会把它们从"看不出来"变成"看得出来"**。

## 5. 这份对照不覆盖什么

- 只截 4 条路由、只 1280×800 一个视口，没看移动端底栏与抽屉。
- 只用 msedge 一个内核；Safari 的 `color-mix()` 与 `backdrop-filter` 表现没测。
- 渐变底/图片底不参与 AA 计数（算不出纯色），那部分只能看截图。
- 没测自定义主题生成器与新皮肤共存时的行为（它按 token 名工作，换 id 不影响，换 token 名会全线破坏）。
- 数字依赖 `scripts/skin-preview.mjs` 里那张映射表（原型 142 token → 产品语义变量）。映射是一次工程判断，若落地时改用别的对应关系，数字会变。

## 6. 建议的顺序

1. 先修第 3 节的三处耦合（本来就是该修的死引用/硬编码），再把 **C → B → A** 落进产品：C 零改动，B 一处文字色，A 一处文字色。
2. **E** 与上面三款一起做也行，但要接受"亮粉降级为纯装饰色"这条约束（否则 10 处里 8 处来自它）。
3. **D** 挂起，等一个更深的紫变体。它其余部分（底色、玻璃模糊、大圆角）在这轮截图里是好看的，缺的只是那颗承载文字的紫。
4. 二次元 8 套本轮按你的指示没测；工具是通用的，`SKINS=f,g,h,i,j,k,l,m node scripts/skin-preview.mjs` 出同一份对照。

## 7. 落地之后的回填（2026-10-12，M23-b / M23-d）

上面的建议有两条被落地时的实测修正了，留在这里以免这份对照继续说旧话：

| 款 | 建议 | 落地实测 |
|---|---|---|
| C 新终端 | 可直接落地 | 已落地（`html[data-theme='terminal']`）。静态门禁 27 项语义配对全达标，扫描贡献 1 处（既有 badge 配对，随后被 `--badge-bg/--badge-fg` 收掉） |
| A 极光夜曲 | "改一处按钮文字色" | 已落地（`html[data-theme='aurora']`），但**不止一处**：该套辅色 `#4FD1C5` 是亮青，`--on-accent` 沿用原型给的纯白得到 **1.87:1**，一次命中 `.filter-tab.active`、`.quick-char-submit`、`.step-flow-row.done .step-flow-no`、`.active-badge`、`.badge-active` 等一批"填充 secondary + 文字 on-accent"的用法。改成该套深墨 `#0A0B14` 后全部达标 ⇒ 落地后对扫描的贡献是 **0 处** |
| B 墨纸 | "一处文字色即可" | **做完又撤出**。27 项语义配对全达标，但真实 DOM 扫描带进 **34 处**低对比配对，与现有 `light` 主题同类的老缺陷（提供方徽章把品牌色写死在组件里压在 badge 底上、`set-primary:hover` 橙压米 3.71）。对比度棘轮基线 131 已被现有皮肤占满，硬塞进去等于把门禁调高，所以等"徽章/提供方色"收口批一起处理；取值与改法在 CHANGELOG 的 M23-d 条目里 |
| E 新粗野 | 限定亮粉用途 | 未落地（同上原因：需要组件侧先不再把 `--secondary` 当文字色用） |
| D 樱雾玻璃 | 等一个更深的紫 | 未落地，缺口不变 |

一句话修正第 3 节那条判断：**"改一处文字色"是就语义配对而言的；真实页面上还有整批"填充 secondary + 文字 on-accent"的组件用法，落地任何亮辅色的皮肤都必须同时定义 `--on-accent`。**
