把手机端从"能用但难用"修到"能正常用"，并把四类已量出的问题闭环：设置分类点不到、群聊消息区塌陷、键盘弹起输入条出视口、焦点逃逸。桌面端守成不动。

- **缺陷修复**：MOBILE_PLAN 批次 0（六项）、批次 1（组成层）、批次 2（导航与形态）。
- **交互优化**：触摸目标 44px 落地（批次 3）、guide 移动端入口、市场叙事降级。
- **重构**：OPT_PLAN 批次 3（专项 B 角色↔世界树绑定）、批次 4（专项 A1 导出落点回显）。

| 字段 | 要求 | 反例（不许这么写） |
|---|---|---|
| 状态 | 已完成 / 进行中 / 未开工 / 阻塞（阻塞须写阻塞源与解除条件）/ 挂起待外部条件 | "差不多了" |

| 解决 | 对应上面的问题，写具体手法；不同问题分行对应 | "已修复" |
| 门禁 | 该轮**实跑读数**，必须带数字。没跑就写"未跑" | 留空 / "应该没问题" |

  4. **9 个调用点全部改走它**：ChatMain（对话导出）、数据面板五处（审核日志 / 备份 / PNG / Markdown / 快捷回复）、character / group-chat / lorebook / story 四个 store（写 `lastInfo`）。
- **遇到的问题**（三条）：
  1. **`cancelled` 一度变成不可达分支**。第一版只在 `env !== 'android-webview'` 时才返回 `cancelled`，而选择器只在 WebView 里用 ⇒ 永远走不到。改成耗时判定后三值都真实可达，也才有得测（单测里用假时钟推进 400ms 模拟"真人点取消"）。
  2. **旧断言钉的正是旧 bug**：`character.test` 有一条"WebView 里取消 ⇒ 返回 false 且不写已导出"——它把"静默"当成了正确行为。改测试时要明确写清"这条以前叫 X，那是旧行为"，否则下一个人会以为是测试坏了。
  3. **Tauri 端拿不到完整路径**（见已知边界），所以没有按 OPT_PLAN 8.2 的原话写"已保存到：完整路径"。文案只说落点类型，不编造路径。
- **解决**：逐条对应；三端 e2e 各一条（浏览器真触发 download 事件、Tauri 注入 `__TAURI_INTERNALS__`、安卓用 `; wv)` UA + 桩）。
- **门禁**：见 §6.3.14。
- **已知边界（三项）**：
  1. **Tauri 端只说"系统下载目录"，拿不到完整路径**。OPT_PLAN 8.2 设想"走既有自定义 Rust 命令"，但全仓只有角色/对话/设置的固定路径命令，没有"保存到用户选定路径"的通用命令；新增要连原生一起验证，而本机没有 cargo（`cargo --version` 不可用），无法实跑门禁 ⇒ 按"不编造"处理，真实路径属 A2（原生插件）范围。
  2. **安卓 WebView 仍是"交给系统下载"，不是真的落盘**。桩的问题没解（要原生插件），本轮只保证"不再静默"——用户至少知道去哪找、知道这条路不通。
  3. **`describeSaveResult` 依赖运行环境判断**（UA + 全局标记）。在浏览器里模拟 Tauri 只能靠注入标记，e2e 就是这么做的；真机仍以真环境为准。

#### M5 · B4（2026-10-19 完成）

##### B4 · 平板档（641–1024）定形 — 已完成

- **开发过程**：一处媒体查询 + 一条定义 + 四条断言。
  1. **先量**：820 / 1000 / 1280 三个宽度各读一次 `.nav-rail` / `.character-list` / `.context-panel` / `.chat-shell` 的盒子。发现 1000 宽时 rail 是 **112px 全宽**，而两侧栏已经抽屉化（`left:-280` / 视口外）——同一档里"半个桌面"，聊天列只有 888px。
  2. **归因**：rail 收窄用的是 `@media (max-width: 900px)`，而 900 是**横屏阈值**（`--bp-landscape-w`），与形态切换无关。真正的形态边界是 1024（`--bp-tablet-max` / JS 的 `isCompact`）。
  3. **改法**：媒体查询 900 → 1024。整档一个形态：**图标 rail（64px，无文字）+ 两侧栏抽屉化（默认收起）+ 无底部导航**。桌面 ≥1025 一行没动。
  4. **断言**：新增 `e2e/tablet-form.spec.ts` 四条——820、1000 各一条（rail ≤64、无文字标签、底栏 0、两侧栏在视口外、聊天列 ≥700）、一条"820 与 1000 是同一形态"、一条桌面 1280 对照（rail >64 且有文字、两侧栏常驻）。
- **遇到的问题**（一条）：**"同一档一个形态"要能被断言，不能只写进文档**。前两条只验"820 长这样"，那 1000 又退回 112px 也照样绿——所以单独加了一条"两个宽度五项读数全等"的用例。这条是本次唯一真正防回归的断言。
- **解决**：逐条对应。
- **门禁**：见 §6.3.15。
- **已知边界（两项）**：
  1. **平板档仍是"桌面导航 + 手机抽屉"的组合**（图标 rail + 抽屉）。另一种候选是"平板也上底部导航"，但那会让 641–1024 与手机完全同形，牺牲横向空间换来的只是少学一套交互——没有证据表明值得，维持现状并把它**定义清楚**（这是判据要求的"明确形态定义"）。
  2. 竖屏平板（如 768×1024）与横屏平板（1024×768）在这一档同形。横屏时高度只有 768，聊天区更紧张，但那是高度问题（另有横屏规则），不在本项范围。

##### 2026-10-18 · A11 角色卡点击行为 → 定乙方案

- **背景**：甲（整卡直进对话）快一步，但编辑入口只能靠长按，不知道长按存在的人等于没有入口；乙（点卡开详情抽屉）四个动作有地方放，但多一步且与"一屏一个主动作"打架。

- **保留**：原文档"甲 + 卡面留一个动作"的倾向未被采纳，但保留在 `MOBILE_PLAN` §6 作为取舍依据。

### 6.5 复盘沉淀（跨任务复用）

**A7 新增的五条（都是会在后续页面上重演的）**：

1. **scoped 样式会压过全局原语**。`.group-body[data-v-x]`(0,2,0) > `.m-swap`(0,1,0)，所以"加一个类就生效"是错觉——`display` 必须由页面自己在媒体块里写，全局原语只管 `[data-level]` 的显隐。A9/A10/A11 接 `.m-swap` 时都会遇到同一件事，别再调试一遍。
2. **`router.replace` 是整体覆盖 history.state**。任何"自己压一层 history"的代码都必须排在路由导航完成**之后**，否则标记被冲掉、返回时先遇到一条空记录。
3. **`<Xxx :title>` 会撞上原生 title 守卫**（`tests/accessibility/no-native-title.test.ts` 只豁免 `<Modal>`）。组件要表达"对话框标题"时叫 `heading`，别叫 `title`。
4. **`display:none` 的元素仍在 DOM**。e2e 里表达"这一级不存在"要用 `toBeHidden()`，用 `toHaveCount(0)` 必红——这条在两级互换类改造里会反复出现。
5. **形态改造要重新走一遍所有进入路径**。群聊的"建群后停在列表级"不是写代码时能想到的：它属于"入口 × 新形态"的组合遗漏。改完组成层，把所有能进这个页面的入口（列表点击 / 新建 / 深链 / 刷新 / 从别页返回）各走一遍，比读代码可靠。

**写断言时踩到的两个坑（记下来防复发）**：

1. **"可达"≠"同时在视口内"**。0-1 最初断言"7 个分类的右边界都在视口内"，三档全红——但那不是缺陷：7 个胶囊内容宽 444px 本就大于 390 视口，**横向滚动条是设计形态**。真正的缺陷是容器自身被撑到 444px、滚动条落到屏外 ⇒ 够不着。改判据为两段：① 容器在视口内（滚动条够得着）② 每项 `scrollIntoViewIfNeeded()` 后完整落在视口内且中心点命中自身。

### 7.4 拆分单元设计（以 R1-1 为例说明切法）

切法固定为五条，后面 23 个文件都按这五条套：

### 7.6 验证方式（每个文件拆完必跑，缺一条不算完成）

| 门禁 | 判据 | 为什么这条对这一项有意义 |
|---|---|---|
| `wc -l` 核对 | 主文件 + 新文件总行数 = 原行数 ±12% | 偏差超 12% 说明搬错了块或漏搬（样板开销约 8%） |
| `vue-tsc --noEmit` | 0 错误 | props/emits 类型是拆分最易断的地方 |
| `npm run lint` | 0 errors | 未使用 import、未定义变量 |
| `npm run i18n:check:strict` | 通过 | 模板搬进子组件后若漏 `t()` 会变成硬编码中文 |
| `npm run check:css-conventions` | 5/5，`!important` 不增 | scoped 样式搬迁后选择器特异性可能变化，守卫会咬 |
| 相关单测 | 该文件对应测试全绿 | 先跑测试再拆（测试即契约），拆完再跑 |
| 对应 e2e spec | 绿 | 例如拆 `GroupChatView` 要跑 `group-chat-flow` + `group-composition` + `group-header-narrow` |
| `npm run check:file-size` | 通过 | 拆完的文件要把白名单里的登记行数改小；降到 800 以下则整条删掉（§7.10） |
| 截图对比 | **批次级，不是文件级**：`node scripts/ui-shot.mjs` 在批次开头与结尾各一次，只人工比对**该批涉及的路由** | 原稿写"每个文件前后各一次"不可行：24 个文件 × 2 次 × 26 张 = 1248 张，且基线会被同批其它文件改动污染，比出来的差异归不到具体文件 |
| 全量 `npm run test` | 0 failed | 每个**批次**结束时跑一次，不是每个文件 |

**"行为零变化"的定义与例外**：拆分 commit 里只允许出现"移动 + import/export + props/emits 接线"，**不允许出现条件分支、样式数值、文案的改动**。

允许一个例外，但必须显式登记：**为保持视觉一致而必需的选择器补位**。scoped 样式随组件搬走后，原来由父级选择器命中的元素可能失配（例如父级 `.group-header .action-btn` 到不了子组件内部），此时补一条等价的子组件内选择器是必要的。这类改动不算违反零变化，但必须满足两条：

1. commit message 里写明"补位：原选择器 → 新选择器，为什么必须补"；
2. 同批的截图比对里，该路由的像素差异必须为零（补对了才没有差异）。

一旦混进真正的行为改动（多一个 `v-if`、改一个间距值），回滚粒度就毁了——这也是"每个文件一个 commit、批次内不 squash"的原因。

| # | 风险 | 应对 |

### 7.8.1 从 R-A 两批得到的结构建议（供二期决策）

1. **先做设计系统原语，再谈"文件大小"**。R1-1 + R1-2 共 +1223 行（+20.6%），其中约 600 行是 `.btn` / `.form-*` / `.detail-*` 的重复副本。行数棘轮压的是"文件多大"，但真正的维护成本是"同一套按钮样式散在 13 个文件里"。建议二期开一项"按钮与表单原语全局化"（`styles/primitives.css` + 保留各视图局部覆盖），做完再回看这些拆分文件的真实体积。
2. **像素比对应该进批次门禁**（现在是人工步骤）。R1-2 的 640 档字号漏抄就是它抓到的，静态守卫当时全绿。脚本已跑通：造数固定时间戳 → 拆前拆后各截一次 → 逐像素 diff；同一版本连跑两次可作噪声对照。

### 7.10 防回长守卫（`check:file-size`）

> §7 是 20–30 人日的投入。没有门禁的话，拆完的 92 个文件半年后会重新长回去——这件事不能靠"下次注意"，只能靠会失败的检查。

**脚本**：`scripts/file-size-guard.mjs`（零依赖，与 `important-guard` / `token-guard` 同一形状：白名单 + 棘轮）
**命令**：`npm run check:file-size`（= `--strict`）；`--list` 只看白名单现状
**CI**：`.github/workflows/ci.yml` 的 `quality-gates` 里，紧跟 `check:css-conventions` 一步

**四条判定**：

| 情形 | 结果 |
|---|---|
| 不在白名单、>1000 行 | **失败**（新长出来的大文件） |
| 不在白名单、800–1000 行 | 警告（进观察名单，不阻断，但评审要说明） |
| 在白名单、当前行数 > 登记行数 | **失败**（拆过的文件又长回去了） |
| 在白名单、当前 ≤800 行 | 通过 + 提示把条目删掉（它的债已经还完） |

**为什么白名单锁"登记行数"而不只锁"存在性"**：只锁存在性的话，文件从 1000 长到 2000 也算通过。§7 的价值全在"它会一直变小"，所以必须对增长有反应。

**登记值上调的条件（2026-10-18 补，A11 第一次撞到）**：棘轮防的是"无声漂移"，不是禁止所有增长。白名单文件因**新增功能**而变大是正常演进，处理方式是——在守卫脚本里显式上调登记值，并在旁边注明"哪一轮功能 + 多少行 + 何时回收（指向 R 类编号）"；只在 commit 里改数字不写原因是违规。**数据文件例外**：i18n 字典标 `ratchet: false`，完全不参与增长判定——每次加 i18n key 都合法，对它套棘轮只会让守卫频繁假红、进而被绕过（比没有守卫更糟）。

**白名单现状**：26 条 = §7.2 的 2 个 i18n 字典 + §7.3 的 24 个目标文件，每条都带 `reason`（未写理由的新增条目评审直接打回）。

**每拆完一个文件要做两件事**（漏了守卫会误判）：

1. 把该文件的 `lines` 改成拆后的实测值；
2. 若拆后已 ≤800 行，整条删除。
