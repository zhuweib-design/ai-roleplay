# Token 体系迁移试点报告（M18）

日期：2026-10-11 ｜ 分支：`feat/ux-ia-guided-flow` ｜ 状态：试点已完成，正式迁移未开始，等三项裁决

## 1. 这个试点要回答什么

用户在 `docs/design/ai-chat-ui-redesign/` 做了一套 token + 原子组件的静态原型（13 套皮肤），要把整个系统的样式换成它。开工前需要先量清三件事：

1. 工作量到底由什么决定（不是行数，是回归面）；
2. 有多少改动是"纯改名"，有多少必然改变画面（必须设计师点头）；
3. 现有代码里有没有会被这次迁移**顺带显形**的历史问题。

试点范围：新建结构层 token 文件 + 只迁移 2 个真实组件（1 个原子组件、1 个面板）+ 一个只统计不阻断的体检脚本。其余 56 个 .vue 一行未动。整个试点是一个可单独回滚的提交。

## 2. 两侧家底（全部实测）

| | 原型 | 产品现状 |
|---|---|---|
| token 总数 | 335 个（结构层 201，每套主题 142） | 145 个唯一变量（含色阶 41） |
| 主题 | 13 套皮肤（同一屏换配色） | 5 套内置（dark/light/midnight/oled/theatre）+ 用户自定义主题 |
| 每套主题重定义 | 142 个变量 | 25–29 个变量 |
| 组件样式 | `components.css` 1,722 行、27 个区块、162 个 BEM 类 | 58 个 .vue 的 scoped 样式共 19,257 行、模板类名 1,409 个（扁平 kebab-case，非 BEM） |
| 颜色取值来源 | 每套主题直写 hex/rgba | 色阶 `--tk-*` + `color-mix()` 派生 |
| 对话框 / 移动端底栏 / 抽屉 / Toast 层 | **原型没有** | 产品有，且各有层级与断点 |

**交集**：变量同名只有 8 个，其中名字和数值都一致的只有 2 个（`--radius-sm` 6px、`--radius-pill` 999px）。所以这不是"改皮"，是换一层契约。

## 3. 决定性数字：多少属性能中性替换，多少必然改视觉

按属性分桶，拿各属性对应的尺度去量（字号用量阶、间距用 4px 阶、圆角用圆角阶），产品 style 块里 3,504 处 px 字面量：

| 属性桶 | 尺度内（可中性替换） | 尺度外（改名即改视觉） | 尺度外占比 |
|---|---|---|---|
| 字号 | 719 | 51 | 6.6% |
| 间隙 | 380 | 204 | 34.9% |
| 内边距 | 564 | 312 | 35.6% |
| 外边距 | 200 | 67 | 25.1% |
| 圆角 | 77 | 6 | 7.2% |
| 边框与焦点环 | 610 | 1 | 0.2% |
| 宽高 | 174 | 139 | 44.4% |
| 合计 | 2,724（77.7%） | 780（22.3%） | |

**那 780 处不是散落的**：仅 6px 与 10px 两个值就占 487 处（尺度外的 62%），再叠加 14px 60 处。也就是说，**在 4px 阶上补两档（6px、10px）**，需要逐处裁决的量就从 780 降到约 230。

字面量颜色：组件层 146 处 / 21 个文件（`src/styles` 里的 248 处是调色板定义本身，不算违规）。

**裁决 3 落地后的复测（实测，不是推算）**：在结构层补 `--space-1-5`(6px) 与 `--space-2-5`(10px) 两档后，用同一把尺重量：

| | 补档前 | 补档后 |
|---|---|---|
| 可像素中性替换 | 2,724 处（77.7%） | **3,181 处（90.9%）** |
| 改名即改视觉 | 780 处（22.3%） | **319 处（9.1%）** |

剩下的 319 处集中在：内边距 14px（48）、宽高 32px（45）、字号 10px（31）、宽高 1px（23）、间隙 14px（12）、外边距 -1px（10）。**其中两类不算真缺口**，是分桶的边界情形：`宽高 1px` 是发丝线、`-1px` 是负偏移，本就不该进间距阶；`宽高 32px` 在间距阶上有值但不在控件尺寸阶上。真正的裁决量因此比 319 还小。

两个试点文件复测后剩余阶外字面量：`StepFlow.vue` 1 处（序号圆 18px）、`ContextReadinessBar.vue` 5 处（3px/5px/7px/1px 一类细调）——都是"补档换不到收益"的零头，按报告第 8 节的口径留待各自区域迁移时逐处判。

## 4. 迁移会顺带显形的历史问题（试点新发现，与迁移本身无关但必须一起处理）

**A 类：裸引用未定义 token，声明今天就是失效的** —— 74 处 / 4 个文件 / 6 个变量名：

| 文件 | 处数 |
|---|---|
| StoryEngineView.vue | 55 |
| CommunityMarketView.vue | 10 |
| WorldBookView.vue | 5 |
| CharacterEditorView.vue | 4 |

涉及的变量名：`--on-surface`、`--on-surface-variant`、`--text`、`--bg`、`--on-bg`、`--border-subtle`。这批命名不是产品的命名体系（产品用的是 `--foreground` / `--background` / `--border` / `--text-muted`），看着像整段外部样式被粘进来后没有改名。后果是**这些颜色与背景声明一直没生效**，页面现在的样子已经不含它们。迁移时逐条要么映射到真实 token（会改变现状视觉），要么删掉死规则（不变）——必须逐处过目，不能机械替换。

试点里就撞到一例：`StepFlow.vue` 的步骤序号圆圈原来写 `background: var(--muted)`，该变量全仓无定义 ⇒ 那圈底色一直没画出来。改成 `--card-elevated` 后它**出现了**，这是一处有意的视觉变化，写在代码注释里。

**B 类：引用未定义但带兜底值** —— 36 处 / 17 个变量名。不报错，但兜底未必是本意：`--primary-foreground` 9 处（产品实际叫 `--on-primary`）、`--range-fill` 7 处、`--surface-1/2/3` 6 处、`--warning` 用于"需注意"状态点（产品只有 `--warning-fg`，没有 `--warning` ⇒ 那三点今天显示的是青色而非琥珀色）。这类要逐条判，估算时按 1 批处理完。

**量过的假阳（写门禁前必须先分类的教训）**：`--range-pct` 由 `el.style.setProperty()` 运行时写入（`src/core/range-fill.ts:25`）、`--bubble-opacity` 由组件 style 绑定写入（`ChatMain.vue:427`），若按"未定义"直接报错就是错的；而 `src/styles` 里的 hex 是调色板定义，混进"组件层写死颜色"会把数量夸大一倍。体检脚本因此默认只统计。

## 5. 三项裁决（2026-10-11 已定，按建议执行）

| 编号 | 待定 | 已采纳的建议与理由 |
|---|---|---|
| 裁决 1 | 皮肤数量：13 套全搬，还是收敛到 5–6 套 | **先收敛到 5 套对齐现状**（dark/light/midnight/oled/theatre），13 套作为"候选配色池"选 5 套定稿。理由：产品每套主题现在只重定义 25–29 个变量，原型每套 142 个——13 × 142 的手工维护量是套数的线性成本，而且自定义主题生成器要跟着长 |
| 裁决 2 | 类名：保留产品现有类名，还是换成原型的 BEM | **保留**。换 BEM 会牵动按类名定位的 11 个单测与多个 e2e（`.lorebook-item`、`.group-item`、`.archive-item`、`.source-return` 等），多花 20–28 批，而视觉收益为零 |
| 裁决 3 | 尺度外那 780 处：补 6px/10px 两档，还是就近归档 | **补两档**。补档只需在结构层加 2 个变量就覆盖 62% 的尺度外量；就近归档会让 487 处元素尺寸变化，等于一次看不见的换肤 |

**落地记录**：裁决 3 已实现为 `--space-1-5` / `--space-2-5` 两档（命名读作“1.5 档 = 6px、2.5 档 = 10px”，注释写在文件里），并当场把两个试点文件中能用半档消掉的 4 处字面量收编。裁决 1、2 是范围决定，不产生代码改动，其后果已计入第 8 节的推进计划。

另有一项是配色而非结构，可以延后：圆角同名不同值（原型 `--radius-md` 10px / 产品 8px、`--radius-lg` 14px / 12px、`--radius-xl` 20px / 16px），试点阶段我按**产品现值**定义，切过去是一次纯视觉决策。

## 6. 单位成本与修订后的总估

试点实测：**一批的时间几乎全花在验证上，不在改样式上**。本批碰了 2 个共享组件，回归面是：对比度门禁（扫 505 处配对）、2175 条组件与核心单测、17 条相关 e2e（含 5 主题 axe 扫描，45 秒）。改动的样式只有 204 行。

据此修订上一轮口头估算：

| 阶段 | 上一轮估 | 试点后修订 | 变化原因 |
|---|---|---|---|
| P0 试点（本报告） | 3 批 | 已完成 1 批 | 建层 + 2 组件 + 体检脚本同批做完 |
| P1 结构层与语义层落地 | 4–6 批 | 3–4 批 | 结构层已落地；剩余是把颜色层收敛成 L2/L3 两段 |
| P2 58 文件迁移 | 18–22 批 | 10–14 批 | 按区域成批（同一次验证覆盖 5–8 个文件）；但 StoryEngineView / ChatMain 这类巨型文件各 2–3 批 |
| P3 死引用与兜底清理 | 未单列 | 3–4 批 | A 类 74 处需逐处判定，B 类 36 处需人判（试点新发现，是真实成本） |
| P4 自定义主题生成器 | 3–4 批 | 3–4 批 | 不变（风险仍在：它硬编码 9 条类规则 + 32 个 token） |
| P5 对比度与主题回归 | 2–4 批 | 2–4 批 | 不变 |
| P6 防回流门禁与文档 | 3–5 批 | 2–3 批 | 体检脚本已成型，接进 Quality Gates 只需把它从统计切 strict |
| 合计（保留类名路线） | 30–38 批 | **24–30 批** | 迁移吞吐上调，但新增死引用清理一块 |

换算：每批约 25–45 分钟（含验证），即 12–20 小时实作；按每天推 3–5 批 ≈ 6–10 个工作日。

## 8. 推进计划（三项裁决已定）

范围由此固定为：**只换 token 层与取值，保留产品类名与 z-index 分层；皮肤维持 5 套内置 + 自定义主题，原型 13 套降级为配色候选池；尺度用"4px 阶 + 两个半档"。**

按区域成批推进，每批一次验证覆盖整族，顺序如下：

| 批次 | 区域 | 为什么排这个位置 |
|---|---|---|
| M19 | 设置面板一族（5 个文件） | 颜色写死最集中、且是主题切换的现场，改完能立刻在 5 套皮肤里看到效果 |
| M20 | 对话区一族（`ChatMain` / `MessageBubble` / 输入区） | 6px 与 10px 的发源地（试点统计里这两个值的大头都在这族），半档的收益要在这里兑现 |
| M21 | 角色与世界书一族 | 含 A 类死引用最密集的 `StoryEngineView`（55 处），需要单独安排一次"死引用清理 + token 化"合并批 |
| M22 | 导航与移动端一族 | z-index 与断点在这里，须与"不采用原型分层"的决定一起验 |
| M23 | 配色定稿批 | 把全部会改画面的东西攒到这里一次看完：圆角同名不同值、A/B 类死引用的映射选择 |

规则：M19 到 M22 期间**结构层与语义层改动保持像素中性**（改完截图对比应当无差异），任何有视觉效果的改动只能出现在 M23。这样才能把"改名"和"换肤"分开评审，也才敢让每一批单独回滚。
