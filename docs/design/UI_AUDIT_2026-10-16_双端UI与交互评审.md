# 双端 UI 与交互评审（2026-10-16）

评审对象：`feat/ux-ia-guided-flow` 工作树（含 6 个未提交改动）。
方法：一手实测为主（真浏览器 + 种子数据），静态审计为辅。**没有代码改动**，本文只出方案。

---

## 0. 结论摘要

1. **桌面端是守成，不是重做。** 三栏对话、九套皮肤、语义 Token 层、对比度门禁都是同类开源项目里偏上的水平。该修的只有三处存量债（死 token 引用、provider 徽章对比度、Token 采纳率 4%）。
2. **手机端的瓶颈已经不在"挤压/溢出"。** 第 15.15 那张常驻网有效：390/360/1440 三档 × 19 路由，挤压 0 命中、横向溢出 0 命中。剩下的问题高一个层级——**手机端没有"组成"这一层**，密集创作页是桌面双栏竖向堆叠，群聊在 390×844 上消息区只剩 103px（12% 屏高）。
3. **最省力的修法不是继续打补丁，而是把自家已有的设计规格补齐。** `docs/design/ai-chat-ui-redesign/docs/05-响应式规格.md` 的 2XS（<768px）段已经写对了：列表转全屏页 + 顶栏切换按钮、面板转全屏抽屉、状态条胶囊横向滚动。成品只在对话页实现了这一段，群聊/世界书/设置三页从未接进来。
4. **对比同类：视觉系统这一层本项目领先，手机端页面组成这一层与 SillyTavern 一样欠账。** 该品类在手机上的通病就是"桌面抽屉 + 密集常驻栏吃屏"——SillyTavern 的社区补丁 Mobilyze 干的就是这件事。手机优先的产品（Character.AI 一类）给的答案一致：一屏一个主动作、聊天占满整屏。详见 §4。
5. **两件事已经做完了，别当新需求重开**：消息列表窗口化渲染（解掉了同类项目最贵的性能坑）、窄屏挤压常驻网（390/360 两档 0 命中）。详见 §6。

## 1. 一手读数（可复现）

量具：`tmp-mobile-audit.mjs`（种角色/对话/世界书/群聊，逐路由按几何判据扫描 + 截图）、`tmp-group-space.mjs`（纵向空间分配）。
跑法：`npx vite --port 5199` → `node tmp-mobile-audit.mjs http://localhost:5199/ 390 844`（另有 360 640 / 1440 900 两档）。

| 判据 | 390×844 | 360×640 | 1440×900 |
|---|---|---|---|
| 竖向挤压（≤12 字被压 ≥3 行且宽 <80px） | **0** | **0** | 0 |
| 横向溢出（scrollWidth − viewport） | **0** | **0** | 0 |
| 可点元素 <44px（每路由命中数） | 7–12 | 7–12 | 12 |
| 输入框字号 <16px（触发 iOS 缩放） | **0** | **0** | 1–10（桌面无影响） |

`--touch-min: 44px` 早在 `tokens.css:152` 定义，但全仓只被 5 处引用；控件阶梯 `--size-control-md: 36px` 被原样带到手机上。**所以 44px 是"写了没执行"，不是"没想到"。**

消息区以上的配置与导航合计 **686px = 81%**。8 条消息挤进 103px 的滚动区里。

### 1.2 世界书页：三层嵌套滚动

390×844 实测滚动容器：`app-shell 844→1087`、`editor-content 521→2092`、`entries-list 227→349`。
即：列表只有 227px（约 1.5 行可见），详情表单 2092px 挤在 521px 的独立滚动区里，外面还套一层 243px 的外滚。桌面上的"左列表 / 右详情"在手机上变成了**同一列里上下两段、各自滚动**，且两段之间没有任何视觉分界或返回动作。

### 1.3 角色列表页：一屏 1.5 张卡

390×844 实测（8 个角色）：

| 区块 | 高 | 占比 |
|---|---|---|
| `characters-header`（标题 + 导入/重生成/新建） | 90 | 11% |
| `search-wrapper` | 36 | 4% |
| `filter-tabs`（11 个标签胶囊，3 行） | 110 | 13% |
| `sort-bar` | 40 | 5% |
| `characters-grid`（可视区） | 443 | 52% |
| 单张 `char-card` | **302** | 36% |

**每屏只能看到 1.5 个角色**，且筛选与排序先吃掉 150px（18%）。卡片本身 302px 里，`card-actions`（编辑/对话/导出/删除 四按钮 2×2）占 62px —— 在浏览列表上给每张卡放四个动作按钮是桌面网格的写法；手机上"点卡进对话"应该是整卡可点，四个动作收进长按或详情页。这不是审美问题：角色多了以后这个列表不可用。

### 1.4 导航

- 底部 Tab **6 个**（会话/角色/市场/世界书/更多/设置），而 `mobile-ui-design.md`、`design-system-specification.md §8`、`software-design-document.md:122` 三处文档都写 5 个。
- 12 条内容入口里 **8 条只能从「更多」进**；另有 **7 个视图进页面就摘掉底部导航**（`mobile-nav.ts:21-31` 硬编码集合），出口只剩各页自己的返回按钮。
- **Android 返回键全仓无处理**：`src/` 内既无 `popstate` 监听，也无 `Capacitor App.addListener('backButton')`。摘掉导航后再按系统返回，行为由 WebView 决定。

## 2. 桌面端（Web）：守成 + 三笔存量债

现状（引用静态审计读数，本文不重复论证）：L1/L2/L3 三层 Token、9 套内置皮肤 + 1 套自定义、`check-contrast.mjs` 26 组语义配对 × 9 款全过、真实 DOM 扫描 506 组配色 × 67 处未过（基线持平）、`Modal` 17 处复用、`EmptyState` 12 视图复用、单一 `nav-model.ts` 驱动四种导航表面。这些是同类项目里少见的秩序。

该修的三笔：

1. **死 token 引用**：`StoryEngineView.vue:1706-2132` 有 55 处引用从未定义的 `--bg / --on-bg / --on-surface / --on-surface-variant`（声明被静默丢弃，那些颜色从没生效过）；`CommunityMarketView.vue:993-1762` 10 处；`WorldBookView.vue` 与 `CharacterEditorView.vue` 各 4–5 处。这不是审美问题，是"作者以为改了颜色，其实没改"。
2. **provider 徽章对比度 1.93–2.10:1**（`SettingsModelPanel.vue`，openai/anthropic 品牌色写死且不随主题走）——全仓最差的两组，且集中在首次配置模型这条必经路径上。
3. **Token 采纳率**：组件层 3665 处字面量 px vs `--space-*` 53 次、`--font-size-*` 34 次、`line-height-*` 0 次。门禁卡住了存量不涨，但也没在降。这是"补丁能不能一处生效"的前提——见 §5-P0-2。

## 3. 手机端：分层看，问题不在同一层

| 层 | 症状 | 根因 |
|---|---|---|
| **L1 结构** | 群聊消息区 12%、世界书三段嵌套滚动、设置 7 个分类横排只露 4 个 | 桌面双栏/多栏直接竖排，**手机端没有独立的"页面组成"定义** |
| **L2 机制** | 96 处断点字面量散在 20+ 文件、`var(--bp-*)` 0 引用、"是否桌面"三套定义（900 / 1024 / 1025） | 响应式是每个组件各自打的补丁之和，没有一处能看到整屏组成 |
| **L3 细节** | 触摸目标 24–37px、`MoreView` 残留 72px 死空白、Toast 在 ≤640 移到顶部盖住 56px 页头、底部 Tab 文字 10px、根节点无 `overscroll-behavior`、长按面板不读 `--keyboard-inset` | 逐条可修，但都要回到 L2 才不复发 |

补一句 L2 的因果：第 15.15 节那三处挤压之所以是"修按钮之后标题又被压"，是因为每个 `@media` 块只知道自己那一小块。有了组成层，这类压力转移会先在设计里暴露，而不是在扫描器里。

## 4. 与同类项目的对比

| 项目 | 手机端现状 | 对本项目的意义 |
|---|---|---|
| **SillyTavern**（同品类基准） | 官方无手机端；Android 走 Termux 或"桌面起服、手机开 URL"。断点 1000px 且**做成用户设置**（`--mobileBreakpoint` + `responsive_layout: auto/desktop/mobile`，带 force-desktop 类）。 | 它的社区补丁 **Mobilyze** 干的事就是本项目现在的问题：收回顶部栏抢走的 15% 竖屏空间、把左右抽屉强制限制在视口内、加浮动消息上下跳转。**这个品类在手机上的通病就是"桌面抽屉 + 密集常驻栏吃屏"**，本项目的群聊页是同一形状。 |
| **SillyTavern issue #5703** | 150+ 条消息时输入聚焦/点击/发送卡 2–3 秒。 | **本项目已解**：`ChatMain.vue:152` 只渲染 `messages.slice(windowStart, windowEnd)` 的窗口（尾部 60 条 + 顶部占位 + 分页加载），并有 `long-history-scroll.spec.ts` 守着。**这条不要重做**，见 §6。 |
| **LobeChat / LobeHub** | 设置走**独立的全页嵌套路由**（`/settings/...`，自带左子导航），手机端退化为汉堡抽屉 + 底部输入区，PWA 可装。 | 与 §5-P0-1 表格里"设置首页 = 全屏分类列表"同一条路。抽屉塞不下 7 个分类是共性问题，不是本项目独有。 |
| **Character.AI 类（手机优先）** | 底部 3–5 Tab（发现/创建/会话/我的）、**聊天占满整屏、无常驻侧栏**、发现页是无限滚动卡片、输入框常驻可及、用户 Persona 是一等对象。 | 与本项目的差距集中在两条：**一屏一个主动作**、**聊天就是整屏**。对照 §1.1：本项目群聊页把 81% 给了配置。 |
| **Apple HIG / Material 3** | HIG：最小命中区 **44×44pt**；按 size class 而非设备布局；主操作用全宽按钮。M3：最小 **48dp**；导航栏 **3–5** 个目的地；移动端编辑器用 bottom sheet 而非居中对话框。 | 三条直接可判：本项目 44px 有 token 未执行（§3-L3）；底部 Tab 6 个超了 M3 上限（§1.4）；世界书条目编辑该是 sheet 不是内联表单（§5-P0-1）。 |
| **Tauri #10631** | Tauri 下软键盘弹出时 `visualViewport.height` **不跟着变**，`innerHeight - visualViewport.height` 这套写法算错。 | `keyboard-inset.ts` 的注释只推演了 Android WebView 与 iOS Safari **两个引擎**，Tauri 是这个仓库的第三个目标却没进这张表。若 Tauri 移动端上马需重验。 |
| **Capacitor #814 / #3229 / #4187** | iOS 键盘收起后命中区不移回（点击落到错误按钮）；Android WebView 长列表滚动后掉帧。 | 前者给 §5-P0-4 加一条验收（键盘收起后复测命中区）；后者已被窗口化渲染规避。 |
| **Capacitor System Bars 插件** | 官方提供安全区/状态栏处理，不建议手写 inset。 | 本项目现在是 4 处手写 `env(safe-area-inset-bottom)`，暂不动；若安卓状态栏/导航栏出现压盖，优先上插件而不是继续加手写。 |
| **SillyTavern #2695** | 升级后设置被清空（数据丢失级别）。 | 与手机无关但同属"结构变更顺手带走数据"这一类，建议在改导航/Tab 顺序前确认设置与分组有兜底。 |

一句话总结对比结果：**本项目在"视觉系统"这一层比同类开源项目强，在"手机端页面组成"这一层与 SillyTavern 一样欠账，而同类里手机优先的产品（Character.AI 一类）给的正是一屏一动作、聊天占满屏的答案。**

## 5. 改进方案

排序原则：先动"一处改、多屏受益"的，再动需要逐页设计的。P0 四条互不依赖，可并行。

### P0-1 给手机端补一层页面组成（最高杠杆）

不是新发明——是把 `ai-chat-ui-redesign/docs/05-响应式规格.md` 的 2XS 段从"只有对话页"扩到全部主页。

| 页面 | 现在的手机形态 | 应改为 |
|---|---|---|
| 群聊 | 列表 18% + 配置 30% + 消息 12%，同列堆叠 | 列表 = 全屏页（顶栏切换钮进入）；进群后配置收进右上"群设置"抽屉；消息区 ≥70% |
| 世界书 | 列表 227px + 详情 521px 双滚动 | 列表 = 全屏页；详情 = 全屏页；条目编辑 = 全屏页 |
| 角色列表 | 单卡 302px，一屏 1.5 张 | 整卡可点进对话；四个动作收进长按菜单/详情页；筛选标签收成一行滚动 + "筛选"入口 |
| 设置 | 7 分类横向 chip，3 个不可见 | 设置首页 = 全屏分类列表；分类 = 全屏页 |
| 故事引擎 / 随机事件 / 数据银行 | 标签页 + 长表单 | 沿用两级的：列表页 → 详情页 |

实现落点：**一个** `src/styles/mobile-composition.css`（或并入 `responsive.css`），定义 `.m-stack → .m-swap` 两级模式（同级互换全屏页），各页只声明"我的列表 / 我的详情"，不再各自写 640 断点里的栏宽和 `vh` 上限。这一步同时把 20+ 文件里的断点补丁慢慢收拢成一个可看的地方。

验收：新增一条 e2e 按几何断言"任一主页的消息/内容区 ≥60% 视口高"，比"没有挤压"更有牙齿——它拦的是结构退化，不是症状。

### P0-2 触摸目标：让 44px 真的生效

`--touch-min` 已有，缺的是落点。两件事：

```css
/* 手机档整体上移一级，而不是给每个按钮加 min-height */
@media (max-width: 640px) {
  :root {
    --size-control-sm: 36px;   /* 28 → 36 */
    --size-control-md: 44px;   /* 36 → 44 */
    --size-control-lg: 48px;   /* 44 → 48 */
  }
}
```

前提是控件高度先走 Token（现在绝大多数是字面量 36px/32px）。**过渡期用一条兜底规则**，只覆盖独立图标按钮与列表行，不覆盖密集行内工具条——群聊那 6 个动作按钮如果各撑到 44px 会再多占 ~60px 竖向空间，先解决 P0-1 再放它们：

```css
@media (max-width: 640px) and (pointer: coarse) {
  .chat-actions button, .mobile-menu-btn, .panel-toggle-btn, .msg-toolbar-btn { min-height: 44px; min-width: 44px; }
}
```

最差的三处先点名：`.composer-btn` 30×30（**比桌面 32×32 还小**，`responsive.css:70`）、`.member-remove` 16×16（`GroupChatView.vue:2309`）、群聊 6 个动作按钮 ~24px 高。

### P0-3 Android 返回键

`popstate` 或 `Capacitor App.addListener('backButton')` 二选一，行为对齐：有抽屉/弹层 → 先关层；在详情页 → 回列表页；在主 Tab → 默认行为（退到桌面）。这条不做，7 个"摘掉底部导航"的页面在真机上就是单向门。

### P0-4 键盘抬升：一个全局变量，一个消费者

`--keyboard-inset` 是全局写的（`main.ts:20` 启动探测），但全仓只有 **1 处**消费——`layout.css:215` 的 `.chat-footer`。也就是说抬升只接线了单聊输入条：

| 需要抬升的 | 类名 | 现在读 `--keyboard-inset` 吗 |
|---|---|---|
| 单聊输入条 | `.chat-footer`（layout.css:204） | ✅ |
| **群聊输入条** | `.input-area`（GroupChatView.vue:1343） | ❌ |
| **长按消息面板** | `MessageActionSheet.vue:80,90`（`position:fixed; bottom:0`） | ❌ |
| 角色列表 / 上下文抽屉 | `position:fixed` 全高抽屉 | ❌（全高可以不管） |

Android 上这个变量恒为 0px（`adjustResize` 已经把布局视口缩了），所以**现在看不出问题**——这正是它活到今天的原因。iOS 一旦成为目标，群聊的输入条会留在键盘底下。修法很小：把 `transform: translateY(-1 * var(--keyboard-inset))` 提到一个共用类（或直接挂到 `.app-shell` 的 `--keyboard-inset` 消费点上），三个消费者共用。

顺带一条来自 Capacitor #814 的验收：iOS 键盘**收起**后要复测命中区是否回位（该 issue 的症状是 UI 移回但点击落点不移回）。

### P1-1 导航：6 Tab 减回 5，并停用"摘导航"策略

- 世界书（2975 行创作工具）下沉到「更多」，**群聊上提到 Tab**。现在手机首屏的 Tab 里放着一个重编辑器，而核心功能群聊要两步才到。
- 那 7 个摘掉底部导航的页面全部恢复保留导航：它们不是沉浸式编辑器，只是内容页。`OPT_PLAN §2.3` 自己已经论证过这一点（`/group` 曾因同样做法变成死胡同）。

### P1-2 常驻 chrome 预算

- **readiness-bar 改横向滚动**：自家规格 `05-响应式规格.md §6` 就写的是"状态条胶囊：横向滚动"，成品却在 `ContextReadinessBar.vue:72` 写 `flex-wrap: wrap` → 69px 两行。改回一行滚动，对话页和群聊页各省 34px。
- `group-capability-note`（55px 散文，内容是"这是设计不是配置问题"）改为首次进入的提示条或折叠项。
- `MoreView.vue:174` 残留 72px 死空白（`App.vue:160-162` 已把底部预留归零）。
- Toast 在 ≤640 落在顶部页头上（`Toast.vue:288-295`）——改成贴底部导航上方，那才是手机上拇指够得着的位置。

### P1-3 断点做成设置，而不是硬规则

SillyTavern 把手机断点做成了用户设置（默认 1000px，可 force-desktop）。本项目的 `viewport.ts` 是全仓唯一 `matchMedia`，加一个"强制桌面布局"开关成本很低，收益是 iPad 横屏、折叠屏展开、以及"我想要桌面版"这类用户不用改代码就能自选。同时它能顺手收掉现有的三套"是否桌面"定义（CSS 900 / CSS 1024 / JS 1025）——统一到一个可覆盖的运行时值。

### P2 三笔存量债

按 §2 的 1/2/3 处理。死 token 引用可以一次清完（纯删除/替换，零风险）；provider 徽章对比度需要给品牌色定一条"作文字时的压深变体"，和之前 `--secondary-text` 是同一手法。

## 6. 不建议做

- **不要动桌面三栏。** 四栏并置是这个品类的核心价值，也是自家原型的第一条设计依据。手机上做减法，桌面上别做加法。
- **不要重做消息列表的窗口化渲染。** `ChatMain.vue:152` 的 `slice(windowStart, windowEnd)` + 顶部占位 + 分页加载已经解掉了同类项目最贵的那个性能坑（SillyTavern #5703，150+ 条时卡 2–3 秒），`e2e/long-history-scroll.spec.ts` 也在守。这条是已经做完的事，别当新需求重开。
- **不要为手机重写一套组件。** 同一个 `Modal`/`EmptyState`/`FilterTabs` 应该继续复用，手机端差异全部落在 CSS 层。一旦分叉出 `MobileModal`，9 套皮肤的对比度门禁要乘 2。
- **不要在真机键盘问题上继续加 `--keyboard-inset` 消费点。** 先把 §5-P0-4 那三处补齐（都是同一行 transform），iOS 真机读数没回来之前不要再扩散——`keyboard-inset.ts` 的 iOS 分支作者已注明未验证。
- **不要为了 P1-1 的 Tab 调整去改 `nav-model.ts` 的数据结构。** 它已经是单一来源，`mobileTab` 顺序改一下就行。
- **不要把世界书条目编辑做成"横向滚动表格"。** 手机上 6 列字段的横滑表格是最坏解；用 §5-P0-1 的"列表 → 详情页 → 字段分组折叠"（同类项目在手机上唯一验证过的形状）。
