## 2. 设计立场

这三条决定后面所有取舍，先立住。

**一、手机是"使用"端，桌面是"创作"端。**
桌面形态是四栏并置的创作工具：rail 112px（≤900px 时 64px，`layout.css:34,104`）+ 角色列表 280px + 自适应主区 + 上下文面板 320px（后两者实测值）。四栏并置本身就是它的价值，不动。手机上要做的不是把四栏挤成一栏，而是承认**手机上做的事不一样**：进来是为了读和回一段对话，不是为了编世界书。所以创作页在手机上明确降级——列表与阅读全功能，重编辑引导回桌面，而不是把 2975 行的编辑器竖着摞起来。

（注：设计原型 `ai-chat-ui-redesign/docs/05-响应式规格.md` 里写的 176 / 275 / 352 是**原型自己的取值**，不是成品现状；以实测为准。）

**这条立场的性质要标清楚**：它是**产品定位判断**，不是实测结论——与立场二（零新增颜色）、立场三（不给内容设 vh 下限）那种可回源复现的证据不属同一强度，别混着用。可证伪条件：若真机数据显示手机上"编辑世界书 / 角色卡"的使用时长占比达到与对话同一量级，这条立场就该改，创作页在手机上就不能只做降级。

这一条与同品类相反。SillyTavern 的社区把完整桌面 UI 往手机上塞，补丁（Mobilyze）干的是"回收竖屏空间、把抽屉限制进视口"——那是在治症状。本项目 84% 的配置占比是同一个病的另一面。

**二、组成层零新增颜色。**
9 套内置皮肤 + 1 套自定义、26 组语义配对 × 9 款全过、真实 DOM 扫描 67 处存量对比度问题——这套体系是资产。组成层只负责重排，不重新着色，一个新颜色都不加。好处是 9 套皮肤和对比度门禁在改造期间读数不变，改造的回归面只有布局。

**三、给 chrome 设上限，不给内容设下限。**
B 的根因是 `.messages-area` 只有 `flex: 1` 而没有 `min-height`：空间不够时它塌到 **0 内容高度**，你看到的 32px 全是它自己的上下内边距。

直觉的修法是"给内容一个下限"，**但那是错的，我试了两版都是错的**：给消息区设 `min-height`（55vh 或 40vh）会与 flex 容器对着干——它要求消息区在视口变小时也占固定比例，于是把输入条挤出视口。实测（390 宽，都先注入组成改动）：

| 方案 | 844 头部 | 844 消息区 | 844 输入条 | 500 输入条 |
|---|---|---|---|---|
| 现状 | 293 | 32（4%） | 812 ✓ | 733 **✗** |
| `min-height: 40vh` | 293 | 338（40%） | 969 **✗** | 831 **✗** |
| 头部 `max-height:110px`（靠裁剪） | 110 | 343（41%） | 791 ✓ | 480 ✓ |
| **动作组/成员条/Runtime 搬进抽屉** | **87** | **367（43%）** | **791 ✓** | **456 ✓** |

所以这条立场的正确表述是：**把竞争者搬走，内容自然长大**。群头部（163–293px）是主要竞争者；靠 `max-height` 裁剪也能达标，但那会切掉成员条——搬进抽屉既不裁东西、结果还更好。凡是以"内容"身份存在的区域，靠限制 chrome 拿到份额，不靠给自己设 vh 下限。

## 3. 设计计划

### 3.1 颜色

**不新增。** 组成层只用既有 token：`--background` / `--card` / `--card-elevated` / `--border` / `--foreground` / `--muted-foreground`，以及既有的 `--z-*` 阶梯（rail 30 < mask 60 < drawer 70 < modal 100 < toast 200）。

**层级也不动。** Toast 在 200 是对的——瞬态系统消息应该盖住一切，包括抽屉。要改的不是它的 z，是它的**位置**：现在 top 12 / bottom 60，正压在 56px 页头上（重叠 44px）；改到贴底部导航上方。理由见 §4。

### 3.2 字体

只改两处，都因为实测数字逼出来的：

| 位置 | 现在（390×844 实测） | 改为 | 依据 |
|---|---|---|---|
| 底部导航标签 | 10px（`BottomNav.vue:78`） | **11px**（`--font-size-xs`） | 6 Tab 时每格 65px；减到 5 Tab 后每格 78px，11px 中文可读 |
| 单聊页头角色名 | `.chat-title` 只有 **62px**（页头固定项：菜单 32 + 分段控件 146 + 动作组 104 + 内边距 16 + 间隙），扣掉头像 24 与间隙，**留给名字约 28px** —— 实测截图里显示成 `S…` | `.chat-title` 拿到 **218px**（名字可用约 184px） | 见下 |

单聊页头的做法：**手机上去掉「对话 / 群聊」分段控件**。它与底部导航表达同一件事（我在哪一屏），是重复的导航。实测把它隐藏后 `.chat-title` 从 62px 变成 218px。

### 3.3 布局

#### 3.3.1 一个原语：`.m-swap`

手机上所有"列表 + 详情"页面共用同一个原语。桌面是并置两栏，手机是**两级互换**，同一时刻只存在一级，靠一条 history 记录切换（系统返回即回列表）。

```
≥1025 桌面                         ≤640 手机
┌────┬─────────┬──────────┐       ┌────────────────────┐
│rail│  list   │  detail  │       │ 全部群聊        ＋ │  ← 列表级：满屏
│    │ ▸ 甲    │  标题    │       ├────────────────────┤
│    │   乙    │  ...     │       │ 打烊之后的三个人   │
│    │   丙    │          │       │ 四个人的长桌       │
│    │         │          │       │                    │
└────┴─────────┴──────────┘       └────────────────────┘
                                   点条目 ↓（pushState）
                                   ┌────────────────────┐
                                   │ ← 全部群聊     ⋯   │  ← 详情级：满屏
                                   ├────────────────────┤
                                   │ 打烊之后的三个人    │
                                   │                    │
                                   │ 消息（≥40%）        │
                                   │                    │
                                   ├────────────────────┤
                                   │ 输入…           ➤  │
                                   └────────────────────┘
                                   系统返回 / ← 全部群聊 → 回列表级
```

要点：

- 一级与二级**都是满屏**，不是"上列表下详情"的同一列两段。这是 B 与 J 的共同修法。
- 顶栏左侧的返回动作**说出目的地**："← 全部群聊"、"← 所有角色"，不是裸的"返回"。
- 二级页里原来挤在一级的东西（群配置、筛选、统计）进二级页自己的入口（群设置、筛选）。
- `nav-model.ts` 已经是导航的单一来源，这条原语不该再造一个来源——它只管"一级/二级"两态，不管有哪些页面。

#### 3.3.2 每个页面在手机上的形态

| 页面 | 现在 | 手机形态 | 一级页顶栏右侧 | 二级页里的配置去哪 |
|---|---|---|---|---|
| 群聊 | 列表 24% + 群头部 30% + 消息 4%，同列 | 群列表 → 群对话 | ＋ 新建群聊 | 成员 / 发言模式 / Runtime → **群设置**（页头 ⋯ 进入，**复用底部抽屉这个形状**——`MessageActionSheet` 已经是正确的抽屉几何 390×357 / 按钮 374×48，但它是消息动作专用的组件，群设置要么泛化它要么照它的几何另写一个，不直接复用组件） |
| 世界书 | 列表 227px + 详情 521px 双滚动 | 世界书列表 → 世界书详情 → 条目详情（**路由三级**） | ＋ 新建 | 绑定角色 / 整体世界描述 → 详情页分组折叠 |
| 设置 | 7 分类横排，3 个点不到 | 设置首页（7 分类全屏列表）→ 分类页 | 无 | 分类页就是二级页，不再有横排条 |
| 角色列表 | 一屏 1.5 张卡 | 保留单栏，但卡不再带四个按钮 | ＋ 新建 | 四个动作 → 整卡进对话 + 长按菜单 |
| 单聊 | 消息区 70%（已经是好的） | 不动结构，只修页头与触摸目标 | — | — |
| 故事引擎 / 随机事件 / 数据银行 | 标签页 + 长表单 | 沿用同一原语：列表 → 详情 | ＋ 新建 | 已是两级，只收窄密度 |

单聊是**唯一不需要组成层改造的页面**（消息区实测 70%）。它的改动只有两处：页头去掉分段控件、工具条图标从 30–32px 到 44px。这条要写进批次里，否则容易被"统一改造"顺手改坏。

#### 3.3.3 底部导航

6 → 5，并让每一个 Tab 都是"每天会去的地方"：

```
现在  [会话] [角色] [市场] [世界书] [更多] [设置]
改为  [会话] [角色] [群聊] [更多]  [设置]
```

- **世界书下沉**：2975 行的创作工具，不该占手机首屏的一个 Tab。
- **群聊上提**：核心功能，现在要两步（更多 → 群聊）。
- **市场下沉**：浏览型功能，且需要登录与网络。它的登录是**本地模拟**——`src/core/community-market.ts:288-300` 的注释就是「模拟登录（按名称查找或自动注册）」，`login(name)` 不收凭据、无后端校验。降级到「更多」的风险低。
- **设置保留**：新用户第一件事是配模型，这条路径不能变长。

那 **8 个**"进页面就摘掉底部导航"的视图全部恢复保留导航——它们不是沉浸式编辑器，只是内容页。项目自己已经为 `/group` 做过同一个判断：`mobile-nav.ts:16-19` 把它移出 `DETAIL_ROUTES`，理由写的是"进 /group 就吞掉底栏会形成单向门"。剩下 8 个是同一个问题（`DETAIL_ROUTES` 9 条路由去重后的 8 个视图）。

#### 3.3.4 对齐

全站左对齐，不做居中标题。中文正文行宽在手机上天然落在 20–26 字，不需要额外约束；桌面侧栏正文已有最大宽度约束，不动。

唯一的例外是空态：空态的图标与主标题居中，说明文字与行动按钮左对齐——**因为说明文字是要读的，按钮是要按的**，居中的多行中文说明会让换行位置随视口跳动。

### 3.4 原则

1. 手机是使用端，创作在手机上降级，不硬塞。
2. 组成层零新增颜色。
3. chrome 有上限，内容不设 vh 下限（40vh 那版实测两档都坏，见 §2 立场三）。
4. 一屏一个主动作。角色卡上四个平级按钮是这条的反例。
5. 44px 是下限不是目标。密集行内工具条可以低于 44px，但要用透明伪元素把命中区撑到 44px，视觉尺寸不变。
6. 一处改、多屏受益优先于逐页调优。

## 4. 自我复核：哪里本来会做成通用默认

按流程复核了一遍，改了三处。

**① 本来会新增一个"移动端强调色"来标记当前层级。**
改成零新增颜色。理由：这个仓库的 9 套皮肤每套有 142 个 token，加一个强调色意味着 9 套都要重新验证对比度，而层级本身已经由"满屏 + 返回目的地"表达了，不需要颜色再加一遍。**改动从"9 套皮肤 × 26 组配对重验"缩小到"布局回归"。**

**② 本来会把所有弹层统一改成底部抽屉。**
实测打脸：删除确认现在是居中对话框（326×225），长按面板已经是底部抽屉（390×357，7 个按钮全 374×48）。**这个分工本来就是对的**——确认类用居中（不遮挡上下文、需要明确点选），编辑器与动作清单用抽屉（拇指可达）。所以方案不改弹层形状。
只记一条**待验证**的：长按面板是 `position: fixed; bottom: 0`，不读 `--keyboard-inset`。这不是疏漏——`OPT_PLAN §15.16` 明确写了"消费点只有一处"并说明理由（"没有同时去抬底部导航——那属于'没设备可看就凭猜改视觉'，先不做"），这个判断是对的。安卓上布局视口随键盘收缩、`fixed` 跟着走，所以**当前目标平台大概率没问题**；iOS 只缩视觉视口才会落到键盘下，而 iOS 不是当前目标。**所以这条只登记，不在本批改。**

**③ 本来会以为 Toast 的问题是层级。**
实测 z=200 已经是全站最高（rail 30 < mask 60 < drawer 70 < modal 100 < toast 200），所以去动 z-index 是白费。真正的问题是**位置**：top 12 / bottom 60，正压在 56px 页头的 44px 上。改成挪到**底部导航上方**，z 不动——手机上拇指够得着的是下半屏，顶部是最贵的地方（那里放着角色名与模式）。

**没改的一条**：`.m-swap` 原语本身是标准的 master-detail 收拢，不算独特。让它站得住的是 3.3.2 那张表——**每个页面的配置具体去哪**，以及"单聊页不需要改造"这个反直觉的结论。

## 6. 已定的一个决定（原 TODO(human)，2026-10-18 决策：乙）

> **决策记录**：2026-10-18，用户定 **方案乙（点卡开详情抽屉）**。三件子问题一并定：① 点卡默认行为 = 开抽屉；② 卡面四个动作（编辑/对话/导出/删除）**全部移出卡面**，只留卡体本身可点；③ 长按菜单降级为快捷方式，不再是唯一入口——因为抽屉里四个动作都是可见按钮。
>
> 下面保留原始两案分析与倾向（甲 + 卡面留一个动作），**该倾向未被采纳**，保留是为了记录取舍依据，不是待办。

批次 1-5 里有一处我不替你定，因为两种答案都站得住，而且选哪个会顺着影响空态、引导与「对话」这个动作在整个产品里的位置。

**角色卡在手机上点一下，应该直接进对话，还是先开一个详情抽屉？**

```
方案甲：整卡直进对话
┌────────────────────┐        点哪里都进对话。
│  ⬤  白栖            │        编辑/导出/删除 → 长按卡片
│  奇幻 · 日常        │
│  一位来自白栖的旅人… │        优点：一屏一个主动作，最符合
│  ⊙ 0 对话   ⚙ gpt-4o│              手机优先产品的做法；
└────────────────────┘              浏览 100 个角色时最快
                                 代价：想改个名字也得先长按；
                                      对不知道长按存在的人，
                                      编辑入口等于消失

方案乙：点卡开详情抽屉，抽屉里一个大的「开始对话」
┌────────────────────┐  点卡 ↓
│  ⬤  白栖            │        ┌────────────────────┐
│  奇幻 · 日常        │        │  ⬤ 白栖      ✕     │
│  一位来自白栖的旅人… │        │  简介 / 标签 / 统计 │
│  ⊙ 0 对话   ⚙ gpt-4o│        │ ┌────────────────┐ │
└────────────────────┘        │ │    开始对话     │ │
                              │ └────────────────┘ │
                              │  编辑   导出   删除 │
                              └────────────────────┘
                                 优点：四个动作有地方放，
                                      长按不再是唯一出路；
                                      适合"先看看是谁再聊"
                                 代价：多一步才进对话；
                                      抽屉里又要放四个动作，
                                      与"一屏一个主动作"打架
```

要定的其实是三件事，答案可以混搭：

1. 点卡的默认行为：进对话 / 开抽屉。
2. 四个动作（编辑 / 对话 / 导出 / 删除）里，哪些留在卡面上？现在四个都在，占 62px。
3. 长按菜单是"主入口"还是"快捷方式"——决定要不要在卡面上留任何可见的编辑入口。

我倾向**甲 + 卡面只留一个动作**：整卡进对话，卡面保留一个"编辑"图标（不占整行），导出与删除进长按菜单。理由是浏览页的主动作是"进去聊"，而"编辑"是第二意图——但第二意图需要**可见**，不能只靠长按。这条是我的倾向，不是结论。

**2026-10-18 决策（乙）与上面倾向的取舍**：倾向甲的核心担忧是"甲的代价——不知道长按存在的人，编辑入口等于消失"。乙把四个动作全放进抽屉，这个担忧自然消失；反过来甲能省的"多一步"在抽屉形态下由抽屉内一个大号「开始对话」补偿。乙的代价是"与一屏一个主动作打架"，落地口径为：抽屉内按"简介/标签/统计 → 开始对话（唯一填充按钮）→ 编辑/导出/删除（次级文字按钮一行）"三级排版，视觉主次靠**尺寸与填充**区分，不靠并列。实施判据见 §8。

## 7. 风险与不做

**风险**

1. `.m-swap` 引入"一级/二级"两态，与 `vue-router` 的既有 17 条路由怎么分工要先说清：建议**不新增路由**，用 `pushState` 一层，避免深链与 `nav-model.ts` 的单一来源被打破。这是批次 1-1 的第一件事。
2. **批次 3-2 让群聊动作行整体变高会再多占约 60px 竖向空间——必须先做完批次 1-2**，否则会把 B 的修法抵消掉。
3. **不要给内容设 vh 下限。** 这是本轮最容易走错的一步：`min-height: 40vh`（甚至 55vh）看着能让消息区达标，实测在 844 和 500 两档都把输入条挤出视口。修法是把竞争者搬走（动作组/成员条/Runtime 进抽屉），不是给内容定比例。也**不要靠 `max-height` 裁头部**——那样能达标，但会切掉成员条。判据必须是**成对的**（消息区占比 **且** 输入条在视口内）——只测前者会得到绿灯而用户打不了字。
4. Tab 从 6 减到 5 要同步改 **两处** `toHaveCount(6)` 断言，不是一处：`e2e/mobile/mobile-layout.spec.ts:49` 与 **`e2e/mobile/mobile-nav-groups.spec.ts:14`**。**只改前者会让后者变红**（两处都是 2026-10-17 回源核出来的，别按"一处"处理）。

   **一处必须纠正的旧判断**：原文曾写"三份文档本来就写着 5 个，改完之后反而变正确了，不需要动"——**这是错的，已更正**。`mobile-ui-design.md:284` 写的 5 个是 会话 / 角色 / **市场** / **世界书** / 设置；方案改完的 5 个是 会话 / 角色 / **群聊** / **更多** / 设置。**计数巧合相同，成员完全不同**，所以改完之后那三份文档（`:17` / `:69` / `:284`）不是变正确，是**变错**——必须同步改成员，不能因为数字对上就不动。

   连带一条：**2-1 必须同时把 `worldbook` 与 `market` 的 `inMore` 置 `true`**（这两项从 Tab 下沉）。否则它们会变成第二个 guide 孤儿——`mobileTab:false` 且 `inMore:false`，正是 IA_EVAL §1.3 / T3 批评的同一个病。判据加一条：`nav-model` 中不存在 `mobileTab:false` 且 `inMore:false` 的条目。

**不做**

- 不动桌面四栏（rail + 角色列表 + 主区 + 上下文面板）。
- 不重做消息列表的窗口化渲染（`ChatMain.vue:152` 已经解掉同类项目最贵的性能坑）。
- 不为手机分叉组件。继续复用同一个 `Modal` / `EmptyState` / `FilterTabs`，差异全落 CSS。
- 不把世界书条目编辑做成横向滚动表格。
- 不在 `--keyboard-inset` 上继续加消费点（先让群聊页自身重排）。
- 不用鼠标事件测长按（`onWrapPointerDown` 要求 `pointerType === 'touch'`，会误判）。
