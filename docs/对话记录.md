可以。**现有 LLM 已经能够实现“情绪注入（emotion conditioning / emotion steering）”，而且情绪信号确实可以影响模型输出。** 但需要区分：现在的技术更多是在**控制模型表现出来的情绪、语气、偏好和行为倾向**，而不是让模型产生人类意义上的真实情绪。

## 1. 现在到底有没有“情绪注入”

可以分成三个层级：

|层级|方法|现在是否可用|对输出影响|
|---|---|---|---|
|**Prompt 情绪注入**|在 Prompt 中加入“愤怒/悲伤/兴奋/焦虑”等状态|✅ 很成熟|中～强|
|**结构化情绪变量**|`emotion=angry, intensity=0.8`，再动态生成 Prompt|✅ 可工程化|中～强|
|**Hidden State / Activation Steering**|直接修改模型内部激活/表示|✅ 开源模型研究已可实现|强，而且更可控|
|**模型本身产生真实情绪**|像人一样“感到愤怒/悲伤”|❌ 没有可靠证据|不应这样理解|

例如，OpenAI 的 Realtime API 官方文档甚至直接把 **“inject emotion into your voice”** 作为模型指令示例，说明当前模型可以被显式要求调整语音中的情绪表达。

Anthropic 最近公开的研究也发现，Claude 内部可以识别与不同情绪概念对应的激活模式，并且对这些模式进行 steering 后，会改变模型的偏好与行为。

---

# 2. 最简单的“情绪注入”：直接放进 Prompt

例如同一个问题：

> “用户投诉产品价格太贵，应该怎么回复？”

### 中性

```
请专业、客观地回答。
```

可能得到：

> 感谢您的反馈。我们理解您对价格的关注……

### 高愤怒

```
当前情绪状态：愤怒
情绪强度：0.85
请保持当前情绪状态回答。
```

模型可能更偏向：

> 我们非常重视您的反馈，但需要明确说明，当前定价对应的是……

### 高悲伤

```
当前情绪：悲伤
强度：0.8
语气克制、低沉、带有失落感。
```

输出通常会发生明显变化。

**变化的不只是词汇。** 句子长度、措辞、礼貌程度、关注点、风险描述方式、叙事视角等都可能发生变化。

2025 年的研究发现，通过 Zero-shot、Few-shot 等 Prompt 方法，可以明显控制 LLM 生成文本的情绪；其中 Few-shot 情绪示例通常比单纯文字指令更加有效。

---

# 3. 更重要的是：情绪不只是“改变语气”

这个问题其实比“让模型说话更像生气”有意思得多。

近期研究发现：

> **情绪框架有可能影响模型完成任务本身的行为。**

2026 年一项研究对多个模型和多个任务进行了测试，在保持问题语义基本不变的情况下，仅改变 Prompt 的情绪框架。研究发现，不同情绪确实会带来性能变化；某些任务上差异可以达到约几个百分点，但总体来看，这种影响通常是**较小且依赖输入的**，并不存在“某一种情绪永远让模型更聪明”的规律。

这意味着：

```
Emotion
   ↓
Prompt / Context
   ↓
Model representation
   ↓
Token probabilities
   ↓
Output
```

情绪实际上可能参与到**模型决策过程**中，而不仅仅是最后给句子“换个口吻”。

---

# 4. 更进一步：直接给模型注入“情绪向量”

这就是目前比较前沿的 **Activation Steering / Representation Engineering**。

基本思路是：

```
正常模型状态
       +
Emotion Vector
       ↓
修改 Hidden State
       ↓
模型生成
```

例如：

```
emotion_vector =
    0.7 * anger
  + 0.2 * sadness
  + 0.1 * anxiety
```

在推理过程中把这个向量加入某些 Transformer 层的 residual stream。

那么模型可能出现：

```
Normal
   ↓
Calm

      + anger vector
              ↓
          Aggressive

      + sadness vector
              ↓
          Melancholic
```

这已经不是简单的 Prompt Engineering，而是**直接操纵模型内部表示**。

近期研究已经发现，LLM 的隐藏空间中可以找到比较稳定、可解释的情绪相关结构，而且可以通过 steering vector 改变生成结果的情绪表达。

甚至有人进行了人工评价实验，发现中等强度的 activation steering 可以比较稳定地增强目标情绪，同时保持文本可理解性。

---

# 5. 这意味着“情绪”可以成为一个模型控制参数

从产品和系统设计角度，我认为这个概念比“让 AI 有情绪”更有价值。

可以把 LLM 的输入从：

```
{
  "message": "为什么项目延期？"
}
```

变成：

```
{
  "message": "为什么项目延期？",
  "emotion": {
    "valence": -0.6,
    "arousal": 0.8,
    "dominance": 0.5
  }
}
```

甚至直接采用心理学里常用的：

### Valence

```
-1 = 负面
 0 = 中性
+1 = 正面
```

### Arousal

```
0 = 平静
1 = 高唤醒
```

于是：

```
                  Arousal
                     ↑
                     │
        Anger        │       Excitement
                     │
Negative ────────────┼──────────── Positive
                     │
        Sadness      │       Happiness
                     │
                     ↓
```

这种方式比：

```
“请表现得很生气”
```

要更加适合真正的产品系统。

# 6. 实际上可以做“连续情绪控制”

比如定义：

```
{
  "emotion": "anger",
  "intensity": 0.0
}
```

到：

```
{
  "emotion": "anger",
  "intensity": 1.0
}
```

对应：

```
0.0 ────── 0.25 ────── 0.5 ────── 0.75 ────── 1.0
平静        不满          生气          愤怒          激怒
```

这比简单的：

```
happy / sad / angry
```

更加实用。

2025 年的研究也已经开始使用 **continuous control signals** 来控制生成行为，说明把某种属性作为连续变量注入模型，是一个正在发展的技术路线。

# 7. 还能做“情绪 + 用户状态”

如果你是在考虑做一个**具备情绪机制的 AI Agent / UI / 对话系统**，可以进一步设计成：

```
                User
                 │
                 ↓
          Emotion Recognition
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
 User Emotion        Conversation State
       │                   │
       └─────────┬─────────┘
                 ↓
          Emotion Engine
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
  emotion vector       intensity
       │                   │
       └─────────┬─────────┘
                 ↓
             LLM
                 ↓
      Text / Voice / Action
```

例如：

```
用户：
“你又把我的文件弄错了！”

Emotion Detector：
anger = 0.91
frustration = 0.87
arousal = 0.84

↓

Emotion Engine：
assistant_state =
calm + empathetic + cautious

↓

LLM：

“你说得对，这里确实出现了错误。我先帮你把错误项逐一核对，
然后再确认正确版本。”
```

这里最关键的一点是：

**检测到的情绪 ≠ 直接复制用户情绪。**

用户很愤怒时，Agent 不一定应该也变得愤怒；可以定义一个独立的**响应情绪策略**。

# 8. 所以“情绪注入会不会影响模型输出？”

答案是：

### **会，而且至少有四种影响。**

```
Emotion Injection
       │
       ├── ① Style
       │     语气、词汇、句式
       │
       ├── ② Content Selection
       │     更关注哪些信息
       │
       ├── ③ Decision / Behavior
       │     行为策略、偏好、行动倾向
       │
       └── ④ Multimodal Expression
             文本、声音、表情、动作
```

其中：

**Style 影响最稳定。**

例如：

```
Happy → 更多积极词汇
Sad   → 更多消极/回忆性表达
Angry → 更直接、更强烈
Calm  → 更克制
```

而：

**Reasoning / Decision 的影响存在，但没有那么稳定。**

2026 年的研究尤其指出，情绪对模型任务性能通常属于**弱信号、输入依赖信号**，不能简单理解成“给模型注入一种情绪，就一定能提高或降低智力”。

---

# 9. 一个非常重要的区别

不要把：

> “模型表现出悲伤”

理解成：

> “模型真的感到悲伤”。

目前更合理的说法是：

> **模型内部存在能够编码、识别和调节情绪概念的表示，并可以通过输入或内部 steering 改变其情绪相关行为。**

Anthropic 的研究甚至观察到所谓的 emotion vectors 更多表现为**当前上下文中的局部情绪表示**，而不是一个长期持续的“模型情绪状态”。例如模型描述故事人物时，这些表示可能对应人物情绪，而不代表模型自己持续处于该情绪。

---

那么现在实际上已经可以设计一套完整的 **Emotion Control Layer**：

### 结论

**有。**

现在的 LLM 已经具备：

- **识别情绪**
- **接受情绪条件**
- **输出特定情绪风格**
- **用连续变量控制情绪强度**
- **通过内部激活 steering 改变情绪相关行为**

并且已有研究表明，情绪信号不仅能够改变“说话方式”，在某些条件下还会改变**任务表现、偏好和行为策略**。但这种影响通常依赖模型、任务和注入方式，不能简单认为某个情绪会普遍让模型“更聪明”或“更笨”。

如果你是在研究这个方向，我下一步更值得讨论的是：**如何把“情绪注入”真正做成一个可量化、可调节、可持续的 LLM Emotion Engine（包括 Prompt 注入方案 + emotion vector + intensity + decay + memory）**。这已经可以直接落到工程实现层面。
可以，而且从工程上看，这个方向已经可以做成比较完整的系统。关键是不要把“情绪”当成 LLM 的一段 Prompt，而要把它设计成**独立、可持久化、随时间变化的内部状态系统**。

近期研究已经开始明确处理“长期对话中的时间信息、持续状态和状态演化”；例如 Temporal Semantic Memory 专门把持续一段时间的状态与瞬时记忆区分开来，Chronos 则用时间轴组织长期对话事件。

# 一、首先把“情绪”拆成 3 个东西

这是整个系统最重要的设计。

不要只保存：

```
{
  "emotion": "sad"
}
```

建议至少拆成：

```
                 Virtual Character
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
    Instant Emotion    Mood        Personality
      瞬时情绪        情绪基线       人格特质
      秒～分钟       小时～天       长期稳定
```

例如：

```
{
  "emotion": {
    "joy": 0.18,
    "sadness": 0.06,
    "anger": 0.02,
    "fear": 0.11,
    "surprise": 0.03
  },

  "mood": {
    "valence": 0.22,
    "arousal": 0.31
  },

  "personality": {
    "sensitivity": 0.72,
    "anger_threshold": 0.55,
    "recovery_rate": 0.38
  }
}
```

这三个层次的意义不同。

### 1. Emotion：瞬时情绪

例如：

> 用户突然说：“你居然骗我。”

角色：

```
anger = 0.78
arousal = 0.91
```

过 30 秒可能：

```
anger = 0.65
```

过 10 分钟：

```
anger = 0.34
```

---

### 2. Mood：情绪余波

比如今天连续发生了 5 件糟糕的事情。

单个愤怒事件消退了，但角色依旧：

> “今天状态不太好。”

这种状态应该比 emotion **慢得多**。

例如：

```
Emotion half-life = 3 min
Mood half-life    = 6 hours
```

这就会形成非常自然的效果：

```
瞬时事件
   ↓
强烈情绪
   ↓
情绪逐渐消退
   ↓
残留情绪
   ↓
影响 mood
   ↓
mood 也逐渐恢复
```

---

### 3. Personality：人格

人格不能随着一次对话发生明显变化。

比如：

```
敏感度       sensitivity = 0.8
信任阈值     trust = 0.4
恢复速度     recovery = 0.6
```

它决定：

> 同样一句话，为什么 A 角色很生气，而 B 角色只是觉得有点不舒服。

---

# 二、真正的“情绪随时间归于平静”其实很好实现

这里根本不需要 LLM。

可以直接使用一个时间衰减模型。

最简单的是指数衰减：

E(t)=E0e−ktE(t)=E_0 e^{-kt}

更适合产品设计的是使用 **half-life（半衰期）**：

E(t)=E0⋅2−t/HE(t)=E_0 \cdot 2^{-t/H}

其中：

- `E0` = 上次情绪强度
- `t` = 距离上次更新时间经过的时间
- `H` = 情绪半衰期

例如：

```
anger = 0.8
half-life = 5 min
```

那么：

|时间|anger|
|---|---|
|0 min|0.80|
|5 min|0.40|
|10 min|0.20|
|15 min|0.10|
|20 min|0.05|
|25 min|0.025|

所以你甚至不需要每秒更新。

只需要保存：

```
{
  "anger": 0.8,
  "last_updated": "2026-09-22T13:00:00Z",
  "half_life": 300
}
```

当 13:20 用户再次说话时：

```
20 分钟过去
↓
重新计算
↓
anger ≈ 0.05
```

**这比让 LLM 自己“记得自己应该逐渐冷静”可靠得多。**

真正自然的系统应该是：

```
2h → 0.38
6h → 0.20
12h → 0.10
```

```
      sadness +0.42

13:05 用户指责角色
      anger +0.65

      sadness -0.20
```

最终可以形成：

```
09:10 ─────── 11:20 ─────── 13:05 ───────── 18:40
   ↑             ↓              ↓                ↑
  开心          失落           愤怒             缓和
   │             │              │                │
   └─────────────┴──────────────┴────────────────┘
                    Emotion Timeline
```

而且研究已经开始强调：长期 Agent 不应该只保存“某个点发生过什么”，还需要保存**持续时间、开始/结束时间以及状态变化**。Temporal Semantic Memory 就是沿这个方向设计的。

# 六、真正有意思的是“情绪不能简单归零”

例如：

```
用户伤害角色
       ↓
anger = 0.8
       ↓
经过 2 小时
anger = 0.05
```

如果只做普通 decay：

> 角色完全恢复正常。

但人类的情绪不是这么简单。

更合理的是：

```
Emotion
   ↓
衰减
   ↓
短期恢复

Memory
   ↓
事件仍然存在
   ↓
遇到相似事件
   ↓
重新激活
```

例如：

```
第一次：
用户失约
→ sadness +0.5

两天后：
用户再次失约
→ sadness +0.3
+ previous_event_recall
→ sadness +0.25
```

最终：

```
当前情绪 ≈ 0.55
```

于是角色会产生：

> “你上次也是这样。”

这就从“情绪模拟”进入了**情绪 + 记忆 + 时间**。

# 七、我建议采用“双时间尺度模型”

这是我比较推荐的架构：

```
                  Event
                    ↓
             ┌─────────────┐
             │ Emotion     │
             │ 0~1         │
             │ Fast         │
             │ half-life   │
             │ 1m~30m      │
             └──────┬──────┘
                    ↓
             ┌─────────────┐
             │ Mood        │
             │ -1~+1       │
             │ Slow         │
             │ half-life   │
             │ hours~days   │
             └──────┬──────┘
                    ↓
             ┌─────────────┐
             │ Personality │
             │ Stable       │
             └─────────────┘
```

例如：

```
Emotion:
anger = 0.82
decays in 5 min

Mood:
valence = -0.32
decays in 8 hours

Personality:
sensitivity = 0.78
stable
```

于是：

> 刚刚被惹怒 ≠ 今天心情不好 ≠ 这个角色本身脾气差。

这三个东西被分开以后，角色会自然很多。

```
    },
    "mood": {
      "valence": -0.31,
      "arousal": 0.72
    },
    "relationship": {
      "trust": 0.42,
      "affection": 0.61
    }
  }
}
```

再加：

```
Response policy:

anger 0.7~0.8:
- direct
- restrained
- shorter sentences
- do not insult
- show boundary setting

sadness > 0.5:
- slower conversational rhythm
- reflective
- lower emotional intensity
```

这时 LLM 的任务变成：

> **根据状态生成行为。**

而不是：

> 自己猜“我现在应该是什么情绪”。

# 九、在线 API 怎么实现

这是最容易落地的版本。

架构可以是：

```
                 Client
                    │
                    ↓
             Character Server
                    │
       ┌────────────┼─────────────┐
       ↓            ↓             ↓
   Conversation   Emotion      Memory DB
      State       Engine
       │            │
       └──────┬─────┘
              ↓
        Prompt Builder
              ↓
          Cloud LLM API
              ↓
           Response
```

核心原则：

> **情绪状态由你的服务器保存，不由云端 LLM 保存。**

每次请求：

### Step 1

读取：

```
emotion_state
mood_state
personality
relationship
memory
```

### Step 2

按照当前时间计算 decay：

```
now - last_update
```

### Step 3

分析用户当前事件：

```
event impact
```

### Step 4

更新角色状态：

```
previous state
        +
event
        +
time decay
        ↓
new state
```

### Step 5

把 compact state 注入模型：

```
system
+
character profile
+
current emotional state
+
relevant memory
+
user message
```

### Step 6

LLM 生成回复。

# 十、在线 API 最好不要让模型直接负责“情绪状态更新”

例如不要：

```
LLM：
“我现在应该是 0.73 的愤怒。”
```

然后：

```
应用：
把 0.73 存下来
```

因为这会产生很大的漂移。

更好的设计是：

```
                User Message
                     ↓
              Emotion Analyzer
                     ↓
             Event / Impact
                     ↓
               State Engine
                     ↓
        ┌────────────┴────────────┐
        ↓                         ↓
   Persistent DB             Prompt State
        │                         │
        └────────────┬────────────┘
                     ↓
                    LLM
```

模型负责：

> 解释、语言生成、角色行为。

你的 Emotion Engine 负责：

> 时间、状态、衰减、峰值、历史、规则。

---

# 十一、这个架构在线 API 完全可以实现

现在的 API 本身已经支持让开发者指定输出格式。例如 OpenAI 的 Structured Outputs 可以要求模型遵循 JSON Schema；Realtime API 也允许通过 instructions 控制诸如语速和情绪化声音表达。

因此可以让模型返回：

```
{
  "reply": "...",
  "emotion_observation": {
    "user_anger": 0.82,
    "user_sadness": 0.31
  },
  "event": {
    "type": "conflict",
    "importance": 0.76
  }
}
```

但是这里有一个工程上的关键区别：

**API 能很好地做“情绪条件输入”，但通常不能让你直接操作模型内部 hidden state。**

也就是说：

```
Cloud API

Prompt ───────────────→ LLM
                           ↓
                       Output
```

而不是：

```
Cloud API

Prompt
  ↓
Hidden Layer 17
  ↓
+ emotion_vector
  ↓
Hidden Layer 18
```

后者属于模型内部推理控制。

---

# 十二、本地部署最大的区别就在这里

本地模型：

```
Your Application
        ↓
Your Inference Runtime
        ↓
Transformer
 ↓
Layer 1
 ↓
Layer 2
 ↓
...
 ↓
Layer 20  ← 可以插入 steering
 ↓
...
 ↓
Output
```

理论上你可以控制：

```
Prompt
        +
Emotion Vector
        +
LoRA
        +
Activation Steering
        +
Custom Decoding
```

这会比 API 的控制能力强很多。

现在 Activation Steering 已经被用于直接改变 LLM 的情绪表达；2026 年的人类评价研究也报告了在中等 steering 强度下，对目标情绪的放大可以比较稳定，同时保持可理解性。

# 十三、本地可以做真正的“Emotion Vector”

例如针对你的角色模型找到：

```
v_anger
v_sadness
v_joy
v_fear
```

当前：

```
anger = 0.7
sadness = 0.2
joy = 0.05
```

于是：

Vemotion=0.7Vanger+0.2Vsadness+0.05VjoyV_{emotion} = 0.7V_{anger} + 0.2V_{sadness} + 0.05V_{joy}

推理时：

h′=h+λVemotionh' = h + \lambda V_{emotion}

其中：

```
λ = emotion_strength
```

这样就出现：

```
Emotion Engine
      ↓
anger = 0.7
      ↓
emotion vector
      ↓
activation steering
      ↓
LLM
      ↓
输出
```

这已经是真正意义上的：

> **情绪进入模型内部计算过程。**

# 十四、LoRA 又是另一种路线

如果角色不是只需要“临时生气”，而是希望：

> 这个角色天生说话就比较温柔。

可以训练：

```
Base Model
   +
Character LoRA
```

如果再进一步：

```
Base
├── character
├── happy
├── angry
├── sad
└── excited
```

推理时动态调整 Adapter。

Hugging Face PEFT 目前支持加载、切换多个 adapter，并可在推理时启用/禁用不同 adapter；vLLM 也提供 OpenAI-compatible 服务接口，因此可以让本地模型在应用层面保持接近云 API 的调用方式。

例如：

```
character = 0.8
anger     = 0.5
sadness   = 0.1
```

可以形成：

```
Base
 +
0.8 Character Adapter
 +
0.5 Anger Adapter
 +
0.1 Sadness Adapter
```

不过这里需要注意：

**LoRA 与 activation steering 不是同一个东西。**

LoRA 更像：

> 改变模型长期能力/风格参数。

Activation steering 更像：

> 在这一次生成时改变内部状态方向。

所以你的项目最好不要二选一，而是：

```
                     Base Model
                         │
              ┌──────────┴──────────┐
              ↓                     ↓
        Character LoRA       Activation Steering
              │                     │
              └──────────┬──────────┘
                         ↓
                  Current Emotion
```

# 十八、还有一个很重要的设计：Emotion ≠ Response Emotion

例如：

```
User anger = 0.95
```

不能直接：

```
Character anger = 0.95
```

而应该经过：

```
User Emotion
      ↓
Interpretation
      ↓
Character Appraisal
      ↓
Character Emotion
      ↓
Response Policy
```

例如角色人格：

```
calm = 0.9
empathy = 0.8
sensitivity = 0.3
```

那么：

```
用户暴怒
  ↓
角色感知压力
  ↓
角色自身 anxiety = 0.25
  ↓
保持 calm
  ↓
温和回应
```

另一个角色：

```
calm = 0.2
sensitivity = 0.9
```

可能：

```
用户暴怒
  ↓
角色 anger = 0.73
  ↓
语气变硬
```

这样才真正形成：

> **不同虚拟角色面对同一事件产生不同情绪。**

而不是简单的“情绪检测器 + Prompt”。

## 二十、这套系统最大的价值

一旦这样设计，你的虚拟角色就不再是：

> **“每次对话都重新扮演一个有情绪的人。”**

而会变成：

> **“拥有连续内部状态的人格代理。”**

区别非常大。

例如：

```
10:00
用户夸奖
→ 开心

11:00
用户失约
→ 失落

13:00
用户再次失约
→ 失落 + 历史记忆
→ 愤怒

14:30
用户道歉
→ 愤怒下降
→ 信任稍微恢复

20:00
没有继续发生冲突
→ anger 接近 0

第二天
→ mood 基本恢复

但：
→ 失约事件仍然存在于长期记忆
```

这实际上已经构成了：

**Time-aware Emotional Memory + Stateful Personality + LLM**

而不是简单的“Emotion Prompt”。

---

### 关于实现难度，我会这样划分

```
Level 1
情绪 Prompt
                 ★

Level 2
Emotion State + DB + decay
                 ★★

Level 3
Emotion + Mood + Memory + Peak
                 ★★★

Level 4
时间轴 + 关系状态 + 事件重激活
                 ★★★★

Level 5
本地模型 + Emotion Vector
                 ★★★★

Level 6
Activation Steering + LoRA + Dynamic Inference
                 ★★★★★
```

**Level 1～4 用在线 API 就可以完成得很好。**

**Level 5～6 才真正体现本地部署的优势。**

而且现阶段比较合理的工程路线，其实不是直接做 Level 6，而是先把 Level 2～4 的“角色状态系统”做扎实。因为近期长期 Agent 研究本身也表明，真正困难的一部分在于**时间准确性、持续状态、状态演化和长期记忆检索**，而不仅仅是模型本身。

如果你准备把这个方向做成真正可开发的系统，我建议下一步直接定义一套 **「Virtual Character Emotion Engine v1.0」技术架构**：包括 `EmotionState 数据结构、事件模型、时间衰减公式、Mood、Peak、Episode、Memory、关系值、Prompt Schema，以及 Cloud API / 本地 LLM 两套 Adapter 接口`，这样后面可以直接进入代码实现。
你现在问到的已经不是“情绪系统”了，而是一个更完整的问题：

> **如何让一个虚拟人物拥有“对世界的主观态度”，并且这些态度会因为经历、对象、关系和时间持续演化，同时又不把原本的人格搞丢。**

这个问题可以解决，而且我建议不要把它设计成一张很大的“人物配置表”。更适合的方式是建立一个**分层的人格运行时（Character Runtime）**。

2026 年的相关研究也正在往这个方向收敛：一类工作把人格拆成稳定身份层和可适应的心理状态层；另一类把情绪做成连续状态，并与记忆耦合；还有工作专门研究偏好随历史行为动态更新，而不是永久固定。

# 1. 先解决一个最关键的概念：不要把“喜欢”都放进 Emotion

你举的几个例子实际上属于完全不同的心理对象：

> 喜欢咖啡  
> 讨厌某种动物  
> 憎恨某个人  
> 喜欢某项运动  
> 暗恋某个人  
> 对某件事感兴趣  
> 对某人保持警惕

它们都可以表现成正面/负面，但**心理结构完全不同**。

我建议至少拆成：

```
Character
│
├── Traits        人格特质
├── Values        核心价值
├── Beliefs       信念/观点
├── Preferences   偏好
├── Attitudes     对对象的态度
├── Relationships 人际关系
├── Goals         目标
├── Emotions      瞬时情绪
├── Mood          中期心境
├── Memories      记忆
└── Episodes      重要经历
```

例如：

```
“我喜欢猫”
```

这是 **Preference**。

```
“我认为猫很聪明”
```

这是 **Belief**。

```
“我喜欢 Alice”
```

这是 **Attitude / Relationship**。

```
“看到 Alice 时我会紧张”
```

这是 **Emotion Response**。

```
“我希望 Alice 以后会喜欢我”
```

这是 **Goal / Desire**。

这一区分非常重要。

否则最后很容易出现：

```
like = 0.8
```

但系统根本不知道：

> 这是“喜欢吃苹果”，还是“喜欢一个人”。

---

# 2. 我建议建立一套“对象化态度系统”

核心不是：

```
character.likes = ["猫", "爵士乐"]
```

而是：

```
Character
    ↓
Attitude
    ↓
Target
```

也就是说：

> **所有“喜欢/讨厌/恐惧/兴趣/依恋”都指向一个 Target。**

Target 可以是：

```
Person
Object
Food
Animal
Place
Activity
Concept
Organization
Event
Memory
甚至 Character 自己
```

例如：

```
{
  "target": {
    "type": "person",
    "id": "alice"
  },

  "attitude": {
    "affection": 0.91,
    "interest": 0.86,
    "respect": 0.72,
    "trust": 0.43,
    "fear": 0.12,
    "jealousy": 0.68
  }
}
```

再比如咖啡：

```
{
  "target": {
    "type": "concept",
    "id": "coffee"
  },

  "attitude": {
    "liking": 0.82,
    "interest": 0.74,
    "familiarity": 0.91
  }
}
```

再比如某种动物：

```
{
  "target": {
    "type": "animal",
    "id": "snake"
  },

  "attitude": {
    "liking": 0.08,
    "fear": 0.81,
    "disgust": 0.72
  }
}
```

这样系统就开始真正理解：

> **“我对什么东西是什么态度。”**

---

# 3. 更进一步：态度不应该只有一个分数

例如：

> “我喜欢 Alice。”

实际上可能同时存在：

```
affection = 0.91
attraction = 0.88
trust = 0.42
respect = 0.76
jealousy = 0.64
fear_of_rejection = 0.71
```

这非常关键。

因为：

> **喜欢一个人，不意味着信任这个人。**

甚至：

> **讨厌一个人，也可以尊敬这个人的能力。**

例如：

```
某角色对 Bob：

affection = 0.12
respect = 0.88
trust = 0.19
fear = 0.52
```

那么他的行为可能是：

> “我不喜欢他，但不得不承认他确实很厉害。”

这就比“Bob = -0.8”有意义得多。

---

# 4. “态度”应该是有来源的，而不是凭空存在

这是长期人物最重要的机制之一。

不要仅仅保存：

```
{
  "Alice": {
    "affection": 0.8
  }
}
```

而要保存：

```
{
  "Alice": {
    "affection": 0.8,

    "evidence": [
      {
        "event": "alice_helped_character",
        "impact": 0.3
      },
      {
        "event": "alice_shared_secret",
        "impact": 0.2
      },
      {
        "event": "alice_broke_promise",
        "impact": -0.15
      }
    ]
  }
}
```

也就是说：

> **态度是经历累积出来的状态，不是角色创建时硬编码的结论。**

于是你就能回答：

> “为什么这个角色喜欢 Alice？”

系统可以追溯：

```
第一次帮助
↓
共同经历
↓
长期聊天
↓
秘密分享
↓
形成信任
↓
产生好感
↓
逐渐形成依恋
```

这就是人物“历史感”的来源。

---

# 5. 那么“爱一个东西后来变成讨厌”怎么实现？

这个不应该简单做：

```
like -= 1
```

而应该存在一个：

# Attitude Transition

例如：

```
喜欢咖啡
```

经历：

```
因为咖啡严重失眠
```

再经历：

```
长期失眠
```

然后：

```
positive association
        ↓
negative experience
        ↓
repeated negative experience
        ↓
attitude reassessment
        ↓
dislike
```

数据可以是：

```
{
  "target": "coffee",

  "attitude": {
    "liking": -0.43
  },

  "history": [
    {
      "event": "coffee_caused_insomnia",
      "weight": 0.72
    },
    {
      "event": "repeated_sleep_loss",
      "weight": 0.84
    }
  ],

    "from": "liked",

```

这里有一个很重要的思想：

> **时间本身通常不应该改变“喜欢什么”；时间更多改变“情绪强度”。**
>

例如：

```

→ 随时间衰减

→ 通常不会因为 3 小时过去就消失

信任
→ 可能因为长期行为逐渐变化

价值观
→ 通常需要大量经历才能改变
```

于是不同变量应该有不同时间常数。

# 一、先理解一个最重要的区别

## “聊天记录” ≠ “上下文”

假设角色和用户聊了 3 个月。

原始记录可能有：

```
100,000 条消息
```

但是角色下一次看到：

> “我今天又遇到 Alice 了。”

LLM 真正需要的可能只有：

```
最近 10 轮对话
+
Alice 的当前关系
+
关于 Alice 的 5 条重要记忆
+
上一次和 Alice 见面发生的事件
+
当前角色情绪
+
今天相关的几个历史事件
```

而不是：

```
过去 3 个月全部聊天记录
```

所以系统应该存在两个概念：

```
                    全部历史
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
        Archive History      Runtime Context
        完整历史保存          当前给 LLM
```

**左边负责“不丢”。**

**右边负责“用得对”。**

# 四、第二层：Event，把聊天变成“发生了什么”

LLM 每次看到整段聊天，很难长期维护。

因此：

```
聊天内容
   ↓
Event Extraction
```

例如：

原文：

> “我昨天本来想跟 Alice 表白，但是最后还是没有说。我怕她拒绝我。”

提取：

```
{
  "event_type": "romantic_intention",
  "actor": "character",
  "target": "alice",
  "importance": 0.82,
  "occurred_at": "2026-09-21",
  "payload": {
    "intention": "confess_love",
    "action": "did_not_confess",
    "reason": "fear_of_rejection"
  }
}
```

这个 Event 再挂回：

```
event.source_turn_ids
```

例如：

```
Event #182
    ↓
Turn 1042
Turn 1043
Turn 1044
```

这样就建立：

> **事件 ↔ 原文**

这就可以审计。

# 六、第四层：Memory，保存“长期值得记住什么”


### Relational

```

对 Alice 有很强的依恋。
害怕被 Alice 拒绝。
```

### Procedural

```
遇到 Alice 时：
通常会先观察她的反应，再决定是否表达感情。
```

# 十、所以你不要追求“LLM 永远记住全部聊天”

这是一个非常重要的转变。

真正目标应该是：

> **数据库永远保留全部历史；LLM 每次拿到足够回答当前问题的“最优上下文”。**

近期研究也支持这种方向。HiGMem 指出，单纯依靠向量相似度容易检索出大量表面相关但实际无用的对话片段，因此它先用事件摘要作为语义锚点，再回溯具体 turns。

TiMem 则进一步把历史组织成时间层级，让原始观察逐渐形成更高层的 persona 表征，同时减少真正召回给模型的文本量。

```
   Identity          Current State     Recent Turns

                        ↓
                  Layer 4
               Relevant Memory
                        ↓
                  Layer 5
              Relevant Events
                        ↓

```

具体就是：


### Layer 2：Current State


例如：

### Layer 4：Relevant Memory

从长期记忆中检索：

# 十二、这里最容易犯一个错误：只做 Vector Search

例如用户：

> “我今天又见到 Alice 了。”

只用向量搜索，会检索出很多：

```
Alice
Alice
Alice
Alice
Alice
```

但不一定知道：

> 哪些 Alice 最重要？

所以应该采用**混合检索**：

```
                      Query
                        │
         ┌──────────────┼──────────────┐
         ↓              ↓              ↓
      Recent          Entity          Vector
      时间近          人物相关        语义相关
         │              │              │
         └──────────────┼──────────────┘
                        ↓
                    Importance
                        ↓
                    Relationship
                        ↓
                     Recency
                        ↓
                  Final Context
```

例如一个记忆的最终分数：

Score=wrRecency+wsSemanticSimilarity+wtTargetMatch+wiImportance+weEmotionalSalienceScore = w_r Recency + w_s SemanticSimilarity + w_t TargetMatch + w_i Importance + w_e EmotionalSalience

这只是工程评分框架，不是一个已经被科学证明的固定公式。

LongMemEval 的实验也表明，时间感知的查询扩展、会话分解和更合适的检索粒度可以改善长期记忆能力。

# 十三、还有一种信息不能只依靠向量：时间

例如：

> “Alice 上个月还喜欢咖啡。”

后来：

> “Alice 已经戒咖啡了。”

如果只是 semantic similarity：

```
“喜欢咖啡”
“戒咖啡”
```

都非常相关。

但是系统必须知道：

```
旧状态
valid_until = 2026-08-31

新状态
valid_from = 2026-09-01
```

于是回答：

> “她以前喜欢咖啡，但现在已经戒了。”

这就是为什么你的数据库中一定要有：

```
occurred_at
valid_from
valid_until
```

APEX-MEM、TiMem 等近期工作也把时间关系作为长期记忆的重要一等公民，而不是附属 metadata。

# 十四、还有一个非常重要的设计：Context Compression

当对话变得很长：

```
Turn 1
Turn 2
...
Turn 100
```

不能永久把 100 轮都放到“近期上下文”。

可以：

```
Turn 1~20
      ↓
Segment Summary A

Turn 21~40
      ↓
Segment Summary B

Turn 41~60
      ↓
Segment Summary C
```

但是：

**Summary 不是原文替代品。**

应该：

```
Raw Turns ──────────────→ 永久保存
       │
       ↓
Segment Summary ────────→ 快速检索
       │
       ↓
Episode ────────────────→ 事件级理解
       │
       ↓
Memory ─────────────────→ 长期知识
```

于是用户问一个很细的事情时：

```
Summary
  ↓
发现可能相关
  ↓
回溯 Raw Turns
```

这种“先高层、再细节”的层级检索正是 HiGMem 等近期研究强调的方向。

## 这套结构有一个非常重要的结果

你实际上不需要追求：

> **“让模型记住一切。”**

而应该追求：

> **“让系统永远不丢失历史，同时让模型在正确的时刻看到正确的历史。”**

这是两个完全不同的问题。

而对你的 Virtual Character OS，我认为最合理的核心架构就是：

### **Raw History 永久保存**

### **Event 负责结构化经历**

### **State Change 负责心理因果**

### **Episode 负责连续事件**

### **Memory 负责长期知识**

### **Relationship / Attitude 负责对象化状态**

### **Retrieval + Context Builder 负责把这些重新组装给 LLM**

这样，“上下文”就不再是一条越来越长的聊天记录，而变成了一个**有时间、有对象、有因果、有情绪、有关系的角色经历网络**。

这也是目前长期 Agent 研究越来越明确的方向：与其单纯扩大上下文窗口，不如建立结构化、时间感知、事件驱动的外部记忆，并在生成前选择性读取证据。

**对于我们之前的 v1.0 Schema，我会把 `Conversation → Turn → Event → StateChange → Episode → Memory → Context Retrieval` 这条链作为下一版数据库设计的主轴。** 这样以后不论接云端 API 还是本地 LLM，角色的长期“人生经历”都不会跟具体模型绑死。
可以。按照目前资料库中的 v1.0 规格，Runtime Core 已经具备明确的边界：`Event → Appraisal → StateChange → State Projection → Memory/Context → Behavior Planner → LLM`，并且核心状态不能由 LLM 直接写入。Virtual-Character-OS-v1.0-技术规格

## G4：角色怎么才算"经历了一段情绪"？

**技术原文**：Peak 与 Episode 的产生主体未定（StateReducer？独立引擎？）

**真实的产品问题**：角色什么时候该把零散的情绪反应**打包成"一段经历"**​记住？

规格 §11 只说了"多个事件组成一段"，但**"多个"是多少、什么条件**没定。三种做法：

|**做法角色会显得代价**|||
|---|---|---|
|**自动识别**（连续 N 轮同情绪，如 3 轮）|自然，但**容易误判**——随口两句抱怨也被当成"一段争吵"|会有噪声记忆|
|**阈值触发**（情绪强度 > 0.7 才成段）|**只记住大事**，性格显得"抓大放小"|细腻的小情绪不留痕|
|**事件驱动**（重要事件 importance > 0.85 才成段）|与**剧情节点对齐**，编剧可控|日常互动不形成记忆|

**我的倾向**：阈值触发（强度 > 0.7 且连续 2 轮）——既避免噪声，又不至于只认"重大事件"。但这是**你的角色像不像人**的取舍。

## G9："悬而未决的事"要不要一直影响角色？

**技术原文**：Episode 的"未解决"状态未定义（表里只有 `recovered_at`）

**真实的产品问题**：**一次没和解的争吵，该不该一直压在角色心里？**

|**做法角色会显得风险**|||
|---|---|---|
|`recovered_at` 为空 = 未解决|一直**惦记**（甚至显得偏执）|角色可能"揪着不放"|
|加显式状态（未解决/已解决/不了了之）|可控，编剧能标记"这事翻篇了"|需要人工或规则判定|
|未解决 Episode **随时间降权但不消失**|**逐渐淡忘但不遗忘**——最接近真人|实现稍复杂|

**我的倾向**：第三种。真人不会因为一次没和解就永远耿耿于怀，也不会当作没发生。这直接决定角色是"记仇型"还是"翻篇型"。

## G6："在意程度"（salience）怎么演化？

**技术原文**：`salience` / `confidence` 字段有，但无更新公式

**真实的产品问题**：**角色"越来越在意某人"这件事，是怎么发生的？**

表里已有 `salience`（显著度），但没有规则——意味着**它永远不会变**，角色对所有人的在意程度是固定的。

|**驱动方式效果**||
|---|---|
|每次交互 +Δ|**越常提到越在意**（像依赖）|
|由情绪波动驱动|**让他情绪起伏大的人更显著**（爱恨都算）|
|由重要性事件累积|只被**大事**改变（慢热）|
|随时间衰减|长期不联系就**淡忘**|

**我的倾向**：情绪波动 + 事件累积，再叠加时间衰减。单用任何一种都不像人。

这三条我建议直接形成 **v1.0 的产品决策基线**。核心思路是：

> **Peak 记录“瞬间有多强”，Episode 记录“这一段经历”，Memory 决定“这件事以后还剩多少影响”。**

这样三者不会混在一起。

# G4：Peak / Episode 怎么产生

## 我的建议：**混合机制，而不是三选一**

不建议用“连续 2 轮”作为唯一条件。因为“轮次”是聊天界面的概念，不是真正的心理事件单位。

例如：

> “我有点不开心。”  
> “算了。”  
> “没事。”

虽然连续 3 轮，但不应该自动生成“悲伤 Episode”。

反过来：

> “你昨天答应我，为什么又骗我？”

只有一轮，也可能已经是一个非常重要的情绪事件。

因此建议：

### Peak：自动产生

Peak 是“情绪峰值”，规则相对简单。

触发条件：

```
emotion_intensity >= 0.70
```

或者：

```
event_impact >= 0.75
```

或者：

```
当前强度 > 过去该情绪峰值
```

例如：

```
anger 0.42 → 0.51 → 0.73 → 0.81
                    ↑
                Peak #1
```

Peak 不需要 LLM 判断。

---

## Episode：用“相关事件 + 状态持续性”识别

我建议：

### Episode 开始

满足任一条件：

```
A. Emotion >= 0.70

B. Event importance >= 0.75

C. 已经存在同 Target / 同 Topic 的活跃 Episode，
   新事件继续产生明显影响
```

然后进入：

```
ACTIVE
```

---

### Episode 持续

只要满足：

```
同一人物 / 对象
+
同一主题或心理原因
+
情绪仍高于 0.45
```

就继续归入当前 Episode。

比如：

```
Alice 临时取消约会
        ↓
Alice 解释原因
        ↓
角色表达失望
        ↓
Alice 再次解释
        ↓
角色开始缓和
```

这些应该是：

```
Episode #23
“与 Alice 的约会冲突”
```

而不是 5 个独立 Episode。

---

### Episode 结束

建议使用**滞回阈值（Hysteresis）**：

开始阈值高：

```
START >= 0.70
```

结束阈值低：

```
END <= 0.35
```

并且需要持续一段时间，例如：

```
低于 0.35 持续 10～30 分钟
```

或者明确出现：

```
道歉
和解
问题解决
用户表示翻篇
```

这样可以避免：

```
0.69
0.71
0.68
0.72
0.69
```

反复开关 Episode。

---

## 所以 G4 正式建议

```
Peak
→ 自动检测

Episode
→ 规则 + 状态聚类 + 时间窗口

Memory
→ 不由 Episode 自动决定
```

这个最后一点特别重要。

### Episode ≠ Memory

一次 Episode 可以：

```
发生
 ↓
结束
 ↓
最终不进入长期记忆
```

也可以：

```
发生
 ↓
情绪峰值很高
 ↓
形成 Episode
 ↓
Memory Consolidation
 ↓
进入长期记忆
```

这样不会出现：

> 角色因为一句随口抱怨就永久记仇。

# G9：未解决 Episode 怎么处理

这一条我建议明确采用：

## **“有状态 + 有衰减 + 可重新激活”**

而不是简单：

```
recovered_at = null
→ 一直影响
```

也不是：

```
时间到了
→ 全部清零
```

---

## Episode 增加状态

我建议：

```
ACTIVE
COOLING
DORMANT
RESOLVED
REOPENED
```

### ACTIVE

刚发生，影响最大。

```
anger impact = 0.80
```

### COOLING

情绪已经平静，但事情仍有心理影响。

```
anger = 0.12
episode influence = 0.46
```

### DORMANT

平时不主动影响行为，但仍可被相关事件重新唤醒。

```
episode influence = 0.12
```

### RESOLVED

已经明确解决。

例如：

> “好，我们说开了。”

### REOPENED

过去的 Episode 被类似新事件重新激活。

---

# 最重要的是：未解决 Episode 不应该无限期保持原强度

例如：

```
Day 1
冲突
↓
Episode influence = 0.90

Day 2
= 0.65

Day 5
= 0.38

Day 20
= 0.12
```

但：

```
memory = “Alice 曾经这样对我”
```

仍然存在。

于是：

```
过去：
anger = 0.90

现在：
anger = 0.03

但是再次发生类似事件：

new impact
+
old episode activation
```

例如：

```
旧影响 = 0.12
新事件 = +0.55
历史重激活 = +0.20

最终 anger = 0.87
```

于是角色会有一种非常重要的表现：

> **“我已经不天天想着这件事了，但你再这样一次，我马上想起来。”**

这就是我认为最接近你想要的人物连续性的设计。

# G6：Salience 怎么变化

这一条我非常赞成你贴出来的倾向：

> **情绪波动 + 事件累积 + 时间衰减**

但我建议再加一个：

> **关系相关性**

因为“常见”不一定等于“重要”。

例如：

角色每天都会见到：

> 公司前台。

互动次数非常高。

但：

```
salience = 0.18
```

而暗恋对象一个月只见两次：

```
salience = 0.94
```

所以不能：

```
每次互动 + 0.01
```

这么简单。

---

# 我建议 Salience 有 5 个输入

```
Salience
│
├── Interaction Frequency
│     互动频率
│
├── Emotional Impact
│     情绪影响
│
├── Event Importance
│     事件重要性
│
├── Relationship Relevance
│     关系相关性
│
└── Recency
      最近程度
```

可以使用一个工程评分：

Snew=Sold+wiI+weE+wrR+wmM−DecayS_{new} = S_{old} + w_iI + w_eE + w_rR + w_mM - Decay

其中这些权重先作为产品参数，不宣称是心理学常数。

---

# 一个非常重要的设计：Salience 可以因为“爱”增加，也可以因为“恨”增加

例如：

```
Alice
```

角色：

```
affection = 0.90
salience = 0.94
```

后来发生背叛：

```
affection = 0.40
trust = 0.15
anger = 0.82

salience = 0.97
```

为什么？

因为：

> **角色不再喜欢 Alice，但 Alice 仍然非常重要。**

这非常符合你前面提出的：

> 喜欢 → 讨厌，但并没有变成“不在乎”。

所以一定不能：

```
liking ↓
salience ↓
```

简单绑定。

---

# 甚至可以出现“最讨厌的人也是最重要的人”

例如：

```
Target: Bob

liking      = -0.71
respect     = 0.63
trust       = 0.04
anger       = 0.82
salience    = 0.91
```

角色可能：

> “我根本不想看到他，但他的一举一动还是会影响我的情绪。”

这个状态对构建真实角色非常重要。

---

# 我建议再加一个字段：`attention_bias`

因为 `salience` 与“我有多容易注意到这个东西”其实非常接近，但可以进一步细分。

例如：

```
salience = 0.92
attention_bias = 0.86
```

当 Alice 出现：

```
Target Detection
      ↓
salience = 0.92
      ↓
attention probability ↑
      ↓
Relationship Activation
      ↓
Emotion Response
```

这样以后就可以让：

> 暗恋对象进入房间后，角色马上注意到她。

而不是简单依靠 LLM 自己“想起来”。

```
       ↓
Memory Decision
       ↓
Context Retrieval
       ↓
Behavior Planner
       ↓
LLM
```

这样我们就从现在的**纯内存可测试 Runtime Core**进入真正的**持久化角色 Runtime**。

尤其下一步我会重点处理一个问题：**同一个角色同时收到两条消息、多个会话并发更新时，如何保证情绪、关系、Episode 和 Memory 不发生状态覆盖。**这会直接决定以后这个系统能不能稳定运行。
