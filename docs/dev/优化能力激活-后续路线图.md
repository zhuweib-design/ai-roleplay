## 1. 核心洞察：两份报告说的是同一件事

| 报告 | 结论 | 指向 |
|---|---|---|
| 对话体验评估 | 「摘要 `summarizer` 已实现但未接线、记忆未持久化」→ 建议**先接线再换模型** | **激活已有能力** |
| 实现对照审计 | 「L1 未接线、三层默认全关」→ 建议**接线 L1 + 明确默认策略** | **激活已有能力** |

**它们不是两个问题，是同一个问题的两种说法**：
项目已经**写好了**一整套对话优化能力（L0/L1/L2 + 摘要 + 记忆），但**没接上、没打开**。

→ **后续工作的第一优先级不是换模型，而是把这套能力真正跑起来。**
→ 这也解释了当前体验痛点（聊久了就忘）：**不是模型不够强，是优化层没生效**。

## 3. 阶段 2：模型升级（按部署形态）

> 前置：阶段 1 完成后再做。否则**换模型会掩盖真正的问题** —— 用大模型的强能力去补工程没接上的缺口，代价高且不可持续。

### 2-A 线上（高配）：接入 `G4-MeroMero-31B`

- **成本**：**零代码**（项目无硬编码模型白名单，改 Profile 的 model 字段即可）
- **收益**：256K 上下文 + RP 专精 + **Apache-2.0**（许可安全）
- **注意**：think/nothink 双模正好配合已有的思考强度控件；上线前**实测中文 RP 质量**（调研未查到公开实测数据）

### 2-B 本地（低配）：注册 `Index-1.9B-Character`

- **成本**：中 —— 需改 `MODEL_REGISTRY`（`local-model-engine.ts`）
- **收益**：1.9B 可 CPU 跑；**RAG few-shot 机制与项目的 lorebook/检索架构天然契合**
- **注意**：本地 `contextLength` **硬编码 4096**，是明确天花板；权重走自定义协议（非 OSI），需确认合规

## 4. 阶段 3：验证与调优

1. **开/关对比实测**：同一段长会话，在「优化全关」与「优化开启」下对比 —— 验证阶段 1 的真实收益
2. **按 §1.2 指标表验收**：核心设定一致率 100%、情绪词保留率 ≥95%、前缀稳定率 100%、输出 token 节省 20-40%
3. **灰度**：按开发文档 §3.4 的路径（基线 → L0 全量 → L2 5% → L1 1% 长会话）
4. **模型侧复测**：换模型后重跑同一组指标，确认是「模型带来的提升」而非「优化层带来的提升」

---

## 5. 推荐起点

**从 1-C 开始（明确默认策略）—— 这是阶段 1 唯一真正待决的事。**

理由：
- 三层**都已实现、都已接线**，唯一的问题是**默认全关**；1-C 直接解决它，成本几乎为零
- ~~1-A 接线 L1~~ 经复核**无需做**（已完整接线）
- **1-B（接线摘要）是本阶段唯一需要写代码的项**：摘要服务有 UI 配置（`SettingsView.vue:1570-1604`）但**无消费方**
- **阶段 2 的换模型放到最后** —— 在优化层没跑起来之前，无法判断体验瓶颈到底来自哪一侧

---

## 6. 一句话总结

> **先把已经写好的东西接上、打开、量出来；确认优化层的真实收益后，再决定要不要为剩下的部分换模型。**
> 顺序颠倒的代价是：花大钱换来的模型能力，被工程缺口浪费掉，而且看不出是谁的功劳。

## 7. ⚠️ 阶段 1 范围修正（2026-09-21 复核后）

实际勘察发现：**阶段 1 比初稿估计的小得多，但性质完全不同** —— 它不是"接线任务"，而是"决策 + 设计任务"。

### 逐项修正

| 项 | 初稿判断 | **复核后实际** | 性质 |
|---|---|---|---|
| **1-A 接线 L1** | 最高性价比待办 | ❌ **无需做** —— 已完整接线 | — |
| **1-C 默认策略** | 改默认值，成本极低 | ⚠️ **是产品决策，不是工程问题** | **需产品拍板** |
| **1-B 接线摘要** | 接线即可 | ⚠️ **需先设计**（见下） | **需设计 + 开发** |
| **1-D 评估脚本** | 中成本 | ✅ 成立，但需 1-C/1-B 落地后才有对比意义 | 开发 |

### 1-C 为什么是产品决策

- **UI 已完整实现**（`SettingsView.vue:2002-2037`：总开关 + L0/L1/L2 三个子开关）
- **且 UI 文案明确写着"默认关闭"**（i18n `settingsView.optDefaultOff`）
- 配置独立持久化在 `localStorage['ai-roleplay:optimization-config']`

→ 也就是说，"默认全关"是**有意的、且已明示给用户的设计**，不是缺陷。
→ 改默认值 = **改变产品行为**，应由产品侧决定，工程侧不宜擅自改。

### 1-B 为什么需要先设计

摘要**不是"接一行"**，它的完整链路涉及三个未决问题：

1. **需要额外 LLM 调用**（`DefaultSummarizationService`）—— 带来成本与延迟，何时触发需权衡
2. **摘要需要存储**（`ConversationSummary` 含 `lastCoveredMessageIndex`）—— 存哪、如何随会话持久化
3. **与 L1 压缩的分工** —— 两者都在处理"长历史"，文档 §3.3 说摘要属 L1 的补充路径，但触发条件（`shouldSummarize` 的 token 阈值）与 L1 的 `decideCompression`（70%/80%）**可能重叠**，需明确谁先谁后

现成接口（可直接用）：`shouldSummarize` / `buildSummarizationMessages` / `injectSummary` / `DefaultSummarizationService`。

### 修正后的阶段 1 建议

**先决策，再动手：**

1. **产品定**：三层默认策略（是否把 L0 默认开）—— 决策后工程侧只需改一个函数
2. **设计定**：摘要的触发时机、存储方案、与 L1 的分工 —— 设计后可实施
3. **工程做**：效果评估脚本（`1-D`），它依赖前两项落地

> **诚实说明**：初稿把"接线 L1"列为第一优先级，是基于一份**误判的审计**（详见
> `embedding-optimization-实现对照.md` §3.2）。复核后确认三层早已接线，
> 真正待办的是**产品决策**与**摘要设计**这两件性质不同的事。
