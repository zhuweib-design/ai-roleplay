# 三层对话优化 · 效果评估脚本使用说明

> 脚本：`scripts/opt-eval.mjs`
> 对应文档：`docs/design/AI酒馆项目嵌入优化方案开发文档.md` §1.2 效果指标（可验证、可验收）
> 首次产出：2026-09-21（寇豆码 / Engineer）
> 本文所有实测数字来自 `node scripts/opt-eval.mjs` 的真实运行，未做任何估算或编造。

---

## 一、为什么需要这个脚本

三层优化（L0 上下文结构 / L1 内容压缩 / L2 输出纪律）在 2026-09-21 已完成接线，
但开发文档 §1.2 承诺的指标（「输出 token 节省 20–40%」「缓存命中 ≥60%」等）
**此前没有任何测量手段**，验收形同虚设。本脚本补上这个缺口：把能离线测的指标
变成可复跑的数字，把测不了的指标明确标注为「需真实环境」而不是编一个数字出来。

脚本只**读取并调用** `src/core` 的导出，**不改动任何业务代码**。

---

## 二、怎么跑

```bash
# 基础：跑离线指标，输出人类可读摘要
node scripts/opt-eval.mjs
npm run opt:eval

# 输出结构化 JSON（便于 CI / 后续分析）
node scripts/opt-eval.mjs --json
node scripts/opt-eval.mjs --out artifacts/opt-eval.json

# 基线
node scripts/opt-eval.mjs --save-baseline     # 存为 artifacts/opt-eval-baseline.json
node scripts/opt-eval.mjs --compare           # 与基线对比，输出增减

# CI 门禁
node scripts/opt-eval.mjs --strict            # 任一离线门禁不达标即退出码 1

# 真实环境探针（可选）
OPENAI_API_KEY=xxx OPENAI_BASE_URL=https://api.deepseek.com \
  node scripts/opt-eval.mjs --with-api

# 其他
node scripts/opt-eval.mjs --target-ratio 0.5  # 改 L1 目标压缩比（默认 0.6）
node scripts/opt-eval.mjs --help
```

**退出码**：`0` = 完成（`--strict` 下表示门禁全通过）；`1` = 门禁失败或运行出错。

### TS 模块的加载方式

项目源码是 TypeScript 且带 `@` 路径别名，纯 Node 无法直接 `import`；项目又没装
`tsx` / `vite-node`。脚本复用 vite 自带的 **esbuild**，把 `src/core` 下待测模块
打成一份临时 ESM bundle（落在 `artifacts/opt-eval-bundle.mjs`，已被 gitignore），
再动态 `import`。因此：

- **不需要新增任何依赖**
- **不改动 `src/` 任何文件**
- 需要项目根目录下 `node_modules` 完整（有 esbuild 即可）

## 三、指标清单：含义与口径

### 3.1 离线可测（脚本实测出数字）

| 指标 | 口径 / 怎么算 | 文档目标 | 本次实测 |
|---|---|---|---|
| **L1 token 节省率** | `countTokens` 实测（gpt-tokenizer cl100k_base）压缩前后 token 差 / 原 token。非估算 | 参考 20–40%（见 3.3 口径警告） | 线上口径 **23.84%**，完整校验口径 **23.39%** |
| **L1 字符节省率** | 字符数差 / 原字符数（token 口径的交叉验证） | — | **27.19%**（完整校验口径） |
| **L1 端到端节省率** | 计入 fail-open 回退后的实际节省（回退则记 0） | — | 线上口径 23.84%；完整校验口径 **0.00%（4/4 回退）** |
| **语义校验通过率** | `validateCompression` 的 `pass` 占比（实体率、情绪率取 min ≥0.9 且关键实体全保留） | 实体/情绪保留率 ≥0.9 | 完整校验口径 **0.00%（0/4）**；线上口径 100%（空校验） |
| **实体保留率** | 分母只取**原文中真实出现过**的实体（用全局声明表做分母会把「样本没提到」误算成「压缩丢了」） | ≥0.9 | **100.00%** |
| **情绪词保留率** | 压缩前后 `EMOTION_WORDS` 命中数对比，两种口径：出现次数 / 去重词 | ≥0.95 | 线上口径 **86.10%**（去重词 88.42%）；完整校验口径 82.75% |
| **对白/情绪豁免** | `classifyScope` 分类正确 + `protect → compressMetaNarration → restore` 后受保护片段、引号对白、情绪词 0 丢失 + standing 豁免黑名单命中 | 硬豁免，0 丢失 | **3/3 分类正确，0 丢失，standing 豁免生效** |
| **L0 前缀稳定率** | `CharacterRegistry.assemblePrefix` 调用 50 次，比较 `prefixHash` 是否逐字节一致；另测写入顺序无关性、scoped 事实隔离 | **100%** | **100.00%（50/50）**，顺序无关 true，scoped 隔离 true |
| **设定静默改写数** | 以 `optimizer` 身份写 standing 事实是否被拦截（修订号是否变化） | **0** | **0 次（已拦截）**，修订号 1 → 1 |
| **压缩管线单次耗时** | 埋点 `extractiveCompress` + `validateCompression`，每样本 20 次，共 80 次采样 | p95 ≤100ms | avg ~0.79ms，**p95 ~1.18–1.76ms**，max ~3.6ms |
| **L2 输出侧 token 节省** | `applyOutputDiscipline` 处理内置样本前后的 token 变化 | 见 3.3 口径警告 | **5.41%**（字符 6.33%），对白/情绪词 0 丢失 |

### 3.2 需真实环境（脚本只声明，不编造数字）

脚本在 `requiresRealEnv` 字段中逐条输出 `status: "requires-real-env"`，并写明原因与测法：

| 指标 | 目标 | 为什么离线测不了 |
|---|---|---|
| 缓存命中率（DeepSeek 前缀段） | ≥60% | 命中率来自 provider 返回的 `usage.prompt_tokens_details.cached_tokens`，离线无任何 LLM 调用 |
| 首 token 延迟 p95 | ≤2.5s | 取决于真实网络与 provider 排队 |
| 输出 token 节省（对话型） | 20–40% | 文档明确要求「真实用量对比（禁止估算）」 |
| 核心设定一致率（≤10 关键事实） | 100% | 需要设定事实测试集 + 真实多轮对话 + 设定抽取判定，三者均不在仓库内 |
| 全量设定一致率（20–50 事实） | ≥95% | 同上 |
| 情绪标签连贯率（相邻轮次） | ≥90% | 需要真实多轮对话的逐轮标注输出 |
| 盲评（关键场景 10 组前文） | 人工评定 | 需人工盲评，样本集尚未提供 |
| BM25 召回耗时 | 软 100ms / 硬 500ms | 属 RAG 指标，不在三层优化评估范围（标 `out-of-scope`） |

`--with-api` 会尝试真实探针：流式请求采样 TTFT，并从 `usage.prompt_tokens_details.cached_tokens`
统计命中率。**没有配置 `OPENAI_API_KEY` 时直接跳过并打印说明，不产生任何数字**；
provider 未返回对应字段时如实标记 `unavailable`。

### 3.3 两条必须记住的口径警告

1. **「token 节省率」不是文档的「输出 token 节省」。**
   文档 §1.2 的「输出 token 节省 20–40%」指的是**模型产出**的 token，且明确要求
   「真实用量对比（禁止估算）」。脚本离线测的是**送入模型的历史（输入侧）** token 变化，
   以及**内置样本**上 L2 规则的削减幅度。两者口径不同，**不可互相替代**，
   脚本中该门禁标记为 `advisoryOnly`（参考），不参与 `--strict`。

2. **L2 节省率对样本高度敏感。**
   `compressMetaNarration` 只删填充词、折叠重复字，且只对 `classifyScope` 判为
   `meta_narration` 的 assistant 消息生效。本次样本中 34 条 assistant 消息的作用域分布为
   对白 7 / 情绪 4 / 状态性 12 / 其他 11，最终只有 9 条被精简。换一批样本数字会明显不同。

## 四、两种 L1 口径：为什么分开测

脚本对 L1 压缩跑两套口径，因为**线上接线与设计文档并不一致**：

| 口径 | 复刻什么 | 结果 |
|---|---|---|
| `asWired`（线上接线） | `src/services/chat-manager.ts:301` 的 `compressMessages(built.messages, pipeline)` —— **未传第三参** | 校验通过率 100%、节省 23.84% |
| `strict`（完整校验） | 显式传入 `entities` / `criticalEntities` / `emotionWords` | 校验通过率 **0%**、端到端节省 **0%** |

根因：`compressMessages` 不传 `options` 时，`runL1` 拿不到 `entities` / `emotionWords`，
`validateCompression` 的三个维度全是空集 → `entityRate` 与 `emotionRate` 恒为 `1`、
`missingCritical` 恒为空 → **校验恒通过，压缩的实体/情绪保护实际未生效**。

反过来的实验也做了：给 `compressMessages` 补传 `entities` 后，压缩条数从 4 条降到
**0 条**——因为 `validateCompression` 以**全局实体表**为分母，单条消息不可能包含
角色卡的全部实体，`entityRate` 天然低于 0.9 → 全部 fail-open 回退。
这是**校验分母设计问题**，不是压缩器问题。

## 五、门禁（--strict）

| 门禁 | 目标 | 本次 |
|---|---|---|
| `compression.entityRetentionRate` | ≥0.9（线上口径） | OK（1.00） |
| `compression.emotionRetentionRate` | ≥0.95（线上口径） | **FAIL（0.861）** |
| `compression.strictValidationPassRate` | =1.0（完整校验口径） | **FAIL（0.00）** |
| `compression.pipelineLatency` | p95 ≤100ms | OK（~1.18ms） |
| `compression.tokenSavingInDocRange` | 20–40% | 参考（0.2384，不参与门禁） |
| `exemption.*`（6 项） | 分类正确 / 0 丢失 / 豁免生效 | 全 OK |
| `l0.*`（4 项） | 前缀 100% 稳定 / 顺序无关 / scoped 隔离 / 0 次静默改写 | 全 OK |
| `l2.outputIntegrity` | 对白与情绪词 0 丢失 | OK |

当前 `--strict` **会返回退出码 1**（2 项未达标）。这是真实结果，不是脚本 bug：
在内置长会话样本上，**情绪词保留率 86% 达不到文档要求的 95%**，因此一旦真正
打开完整校验，L1 会因为校验不通过而 100% 回退原文、收益归零。

## 七、已知边界与后续建议

1. **发现的问题（建议跟进）**
   - `compressMessages` 未传 `entities` / `emotionWords` → 语义校验形同虚设，
     情绪词保留率 86% 却毫无拦截。
   - `validateCompression` 用全局实体表做分母，对单条消息天然偏严 → 一补传
     `entities` 就 100% 回退。建议改为「原文中实际出现的实体」做分母。
   - `classifyScope` 要求引号内容占比 ≥50% 才判为对白，因此「短对白 + 长旁白」
     的混合句（如引号占比 36.84%）会落到 `meta_narration` 进入可精简集合。
     内容不会丢（引号已被 `protect` 哨兵保护），但如果需要这类句子也硬豁免，
     需要调阈值。脚本已把这条作为「边界观察」如实输出，不设门禁。

2. **样本是内置的、合成的。** 脚本自带 72 句中文角色扮演长会话（含对白、情绪旁白、
   状态性旁白、世界观实体），用于保证可复跑。若要更贴近线上，建议后续接入
   脱敏的真实长会话样本（文档 §2.2 提到「100+ 轮长会话」由运营提供）。

3. **真实环境探针未做过实跑验证。** `--with-api` 分支已实现，但当前环境没有
   API 凭据，只验证了「无凭据时正确跳过」这一路径；实际请求分支尚未跑通过，
   首次使用请留意 `errors` 字段。
