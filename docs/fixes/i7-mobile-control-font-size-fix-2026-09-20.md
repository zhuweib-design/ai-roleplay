## 一、交付内容

### 1.1 守卫合并（`quality-gates` 10 → 7 道）

新增 `scripts/css-conventions-guard.mjs` 作为**子进程编排器**，依次调用 5 个子检查，任一失败整体 `exit 1` 并指明是哪一项。

`.github/workflows/ci.yml` 中原本 4 个独立的 CSS 守卫步骤合并为 1 个 `check:css-conventions`：

```
lint → i18n strict → CSS conventions（5 项子检查） → 对比度 → 覆盖率 → 构建 → CSP
```

**设计取舍**：编排器**不复制任何检查逻辑**，判定语义 100% 由原子脚本决定 —— 逻辑只有一份，天然不会漂移；4 个原子脚本与 npm 命令保留，供本地针对性调试。CSP 守卫仍保持在 `Build` 之后（它校验 `dist/`）。

### 1.2 新增 I-7 门禁

`scripts/i7-control-font-size-guard.mjs`：

| 检查 | 语义 |
| --- | --- |
| **硬检查**（阻断） | 移动断点内须存在覆盖 `input`/`textarea`/`select` 且 `font-size ≥16px` 的**全局兜底**；只认**裸元素类型选择器** |
| **告警**（不阻断） | 仅对「**未覆盖**」的 <16px 控件选择器告警 |

识别「可编辑控件」的手段：元素类型选择器 ∪ `[contenteditable]` ∪ **模板反查得到的控件类名**（扫描 `.vue` 中 `<input>/<textarea>/<select>` 标签的 class，**仅保留只出现在控件标签、未出现在其他元素上的类名**以抑制误报）。

## 二、修复的真实缺陷：iOS 聚焦放大

### 2.1 根因

`src/styles/app-global.css` 的全局兜底：

```css
@media (max-width: 640px) {
  input, textarea, select { font-size: 16px; }   /* 特异性 (0,0,1) */
}
```

被组件 scoped 规则压制，例如 `CharacterVersionView.vue` 顶层：

```css
.form-group input, .form-group select, .form-group textarea { font-size: 13px; }  /* scoped 后 (0,2,1)+ */
```

**特异性更高者胜出，与是否位于媒体查询内无关** → 兜底写了但**从未生效**，移动端控件实际仍是 13px/12px，iOS 聚焦照旧放大页面。

### 2.2 修复方式（逐组件）

25 个文件（24 个 `.vue` + `src/styles/layout.css`）在各自 `<style scoped>` **末尾**追加一个 `@media (max-width: 640px)` 块，用**与原规则完全相同的选择器**覆盖为 `16px`。

**原理**：媒体查询**不影响特异性**；同特异性下由**源码顺序**决定胜负 → 置于末尾即稳定胜出。

**未采用的方案**：在全局兜底上加 `!important`（可 1 行修复，但项目 `!important` 棘轮基线须保持 46 不变，且属 hack）。

**桌面密度不变**：顶层 13px 规则有意保留，仅 ≤640 生效。

## 五、遗留与证据边界（诚实标注）

| 项 | 说明 |
| --- | --- |
| **D3 不建模 CSS 特异性** | 「已覆盖」是静态判定（同文件 + 同选择器 + 源码顺序）。本仓库 D1 恰好用**完全相同的选择器**，故判定成立 —— 这是**前提**，已写入守卫注释。**若覆盖块换用更弱选择器会假「已覆盖」** |
| **硬检查过严** | 只认裸元素类型选择器，`:where(...)`/`body input` 会误报失败。属**安全方向过严**（fail-closed），可接受，已在注释声明 |
| 未测真机 iOS Safari | 仅测 chromium；但 `font-size < 16px` 正是触发条件，判据充分 |
| 两个模态为间接验证 | `SceneConfigModal` / `TemplateEditorModal` 未实际点开，其覆盖由组件块保证 + 静态判据 |
| 1 条 E2E flaky | `character-crud`，重试即过，与字号改动无关，未断定是否本次引入 |

## 六、过程教训（主理人自省）

1. **验收标准写错**：曾把「I-7 告警降到 0」定为验收标准，但守卫当时告警的是**原始 <16px 声明**（有意保留给桌面），该标准**根本不可能达成**。**教训：给门禁定验收标准前，先确认该标准在目标语义下是否可达。**
2. **约束范围表述不清**：把「不要动 `src/`」这条**只约束某一阶段**的指令与后续任务范围写在一起，导致工程师停下确认。**教训：多阶段派单时，约束须写明「仅适用于本阶段」。**
3. **执行障碍**：工程师曾连续两轮只做前一项任务就结束，后改为「极具体清单 + 拆 5 批 + 每批回报」才推进；另有一次因 **429 频率限制失败**，但失败前已完成 24 个文件的改动且质量正确。
