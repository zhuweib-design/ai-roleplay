## 1. 产品定位

### 1.1 目标用户

三层同心圆，越往外越难留住：

1. **核心（作者本人 + 模型使用者）**：已经下载了 Tifa-Deepsex 系列 GGUF 的人。他们要的不是"又一个 ChatGPT 界面"，而是"能让这个模型发挥出来的界面"。
2. **中间（轻量 Ollama 用户）**：不想装 Docker、不想起 Python 服务，只想双击一个 HTML 就开始聊的 Windows 用户。
3. **外围（泛 RP 爱好者）**：被"思维链 + 角色扮演"关键词吸引来的尝鲜者（issue 区大量"怎么配置/选不到模型"来自这一层）。

### 1.2 解决的痛点

| 痛点 | 它的解法 | 有效性 |
| --- | --- | --- |
| Open WebUI 要 Docker、太重，我只想聊自己那个 7B 模型 | 一个 HTML + 一个 .bat，双击即用 | 高（Windows 上）；Mac/Linux 上退化（issue #1/#4/#9/#8） |
| 推理模型的思考过程被主流前端吞掉或显示成一坨 | 解析 `<think>` 渲染为可折叠"思考过程"块 | 高，且是它最早（0215）的差异化点 |
| RP 输出的长度/文风/节奏不可控，全靠手写提示词 | 风格控制面板：4 个控件 → 编译成提示词后缀 | 中高（机制聪明，但强绑定特定模型） |
| 对话关掉浏览器就没了 | localStorage 自动保存 + 多会话列表 | 中（够用，但清缓存即失，无导入/导出 JSON） |
| 手机上想继续聊 | `<768px` 侧栏抽屉 + 媒体查询 | 中（响应式做了，但输入框/状态栏在小屏拥挤） |

### 1.3 核心使用场景（客观描述产品机制）

- **场景 A｜带推理的对话**：开"深度思考：低/高"，模型先产出 `<think>` 推理再作答，前端把推理折叠、作答渲染为 Markdown。
- **场景 B｜参数化叙事**：在右侧"角色扮演控制"面板调文笔风格/字数/旁白占比/剧情节奏，控件值被编译成一段结构化文本，自动追加到每条用户消息尾部，模型据此调整输出形态。
- **场景 C｜带状态的角色扮演**：开启"状态栏"后，模型在回复里输出结构化键值（地点/时间/NPC/好感/想法等），前端识别后渲染成可拖动的浮动状态卡。
- **场景 D｜多会话留存**：左侧会话列表，每个会话独立保存消息、系统提示词与所用模型。

> 注：场景 B/C 依赖特定模型遵循约定，面板上直接标注"仅支持 UltraV2"。

### 2.2 演进逻辑：三阶段

```
阶段一（0215–0216）「能聊」
  支持 <think> + 可改系统提示词
  → 让自家 CoT 模型"能用"，这是它存在的理由

阶段二（0223–0302）「聊得舒服」
  高级参数 → 撤回/导出 → 欢迎页/自动保存/多会话/手机适配/自定义API
             → 复制/重新生成/代码浮动/加载页/主题
  → 补齐一个现代聊天 UI 的"及格线清单"，密集迭代（6 周内 3 个大版本）

阶段三（0325）「可控可调」
  风格控制面板 + 数学公式 + 防误触 + 状态栏精致化
  → 从"通用聊天壳"转向"RP 专用控制台"，这也是它真正的差异化落点
```

**产品判断**：它的演进不是被用户需求驱动，而是被**模型能力驱动**——每次模型出新版本（0215 CoT、0301 Cot-0301、0325 NoCot-0325），前端就同步加一波对应能力。这是"模型作者的配套壳"的典型节奏：**UI 是模型能力的曝光面**。

边际递减也很明显：0325 之后到 2026-08 只剩 README 链接更新，两个社区 PR（#3 模型名超长截断、#10 修复导出）至今未合并。

## 3. 产品机制拆解（它做对了什么）

这一节是**最值得借鉴的部分**，均来自源码阅读。

### 3.1 思维链：UI 层极简，语义层克制

```js
// 渲染：把 <think> 替换为可折叠容器（默认展开）
content.replace(/<think>|<\/think>/gi, ...)

// 回传：历史中 assistant 的 think 先剥掉再发给模型
content: msg.role === 'assistant'
  ? msg.content.replace(/<think>[\s\S]*?<\/think>/gi, '').trim()
  : msg.content.trim()
```

一个容易被忽略但很关键的设计：**思考过程只用于给人看，不回灌给模型**。避免上下文被推理文本挤爆。这一点很多前端没做。

### 3.2 "深度思考级别"：用提示词注入模拟推理预算

```js
if (deepThinkingLevel === 1) lastUserMsg.content += "\n\n使用<think>思考900字";
else if (deepThinkingLevel === 2) lastUserMsg.content += "\n\n使用<think>思考1800字";
```

三档循环按钮（关 → 低 → 高），状态存 localStorage。**成本近乎为零，但给了用户一个"推理强度"旋钮**——对于不支持原生 `reasoning_effort` 参数的本地模型，这是唯一可行的路径。缺点是脆弱（模型不听话就失效），但作为"可选增强"完全成立。

### 3.3 风格控制面板：UI 控件 → 提示词编译器（核心创新）

右侧"角色扮演控制(仅支持UltraV2)"面板：

| 控件 | 取值 | 语义 |
| --- | --- | --- |
| 文笔风格 | 0-3 滑块 | 精准 / 智能 / 文艺 / 发散 → 映射为「严谨工整标准 / 清水文标准 / 好文笔活泼 / 深度思考发癫文学文艺」 |
| 预计输出字数 | 100–2000，步长 100，默认 200 | 直接写进指令 |
| 回复偏好（旁白占比） | 1–5，默认 2 | ≤2 低 / ≥4 高 / 其余 中 |
| 剧情节奏 | 慢 / 中 / 快 | 段落长度 250 / 140 / 90 字 → `段落数 = round(字数 / 段落长度)` |
| 状态栏开关 | on/off | 是否要求模型输出状态块 |

编译产物（写入 `localStorage.novelSettings`，并**追加到每一条用户消息**）：

```
{
  风格：清水文，标准
  字数：500字
  段落：4
  对话占比：低
  状态栏：关
}
```

**产品含义**：它把"写提示词"这件事变成了"拖滑块"。RP 用户最大的痛苦不是不会聊天，而是"输出太长 / 太短 / 文风不对 / 旁白太多"——这些恰恰是**连续的、可枚举的、可结构化的**维度，非常适合做控件化。这是它比 Open WebUI 更懂 RP 用户的证据。

**但它也暴露了三个问题**：① 面板效果强绑定单一模型（标注"仅支持 UltraV2"）；② 编译结果对用户不可见（只 `console.log`）；③ 无条件追加到每条消息，无法按会话/角色关闭。

### 3.4 状态栏：把代码块"劫持"成角色状态卡

模型输出被 ``` 包裹的键值文本时，前端按 /^[\s\S]*[\u4e00-\u9fa5\w]+:/ 判定，逐行按 `:` 拆分，按 key 关键词加图标：

`地点/位置/场景` → 🧭 ｜ `时间/日期` → ⏱️ ｜ `NPC/角色/人物` → 👤 ｜ `好感/关系` → 💗 ｜ `想法/思考` → 💭

值过长（>20 字或含换行）自动切换为竖排布局，可拖动、可关闭。

**产品含义**：用零结构化成本（不要求 JSON、不要求 schema），把模型的"自由文本输出"变成"沉浸式的实时状态 HUD"。这是 RP 场景里"代入感"的直接来源。代价是**完全靠正则猜**，模型格式一变就崩。

### 3.5 其它细节

- 生成中给侧栏加 `pointer-events: none`——防止用户中途切换会话导致上下文错乱。
- 复制时自动剥离 `<think>`；导出时也剥离。
- 撤回按"最后一条是 user 删 1 条、是 assistant 删 2 条"智能判定。
- 字体走中科大镜像（`fonts.proxy.ustclug.org`），是明确的国内网络适配。

### 4.1 对比结论

- **它不是 Open WebUI 的竞品，是"补位者"**：Open WebUI 解决"团队/家庭的 AI 门户"，它解决"我一个人、一个本地模型、现在就要聊"。两者用户重叠度低。
- **它真正的对手是 SillyTavern 的"轻量版"**：RP 用户要么忍 SillyTavern 的部署门槛，要么忍受无角色卡的简陋。它卡在中间的"轻量 + 有 RP 专属控制"位置——而角色卡（它自己的更新计划第一项）恰恰没做。
- **Cherry Studio 是它的降维打击者**：同为"开箱即用、中文用户友好"，Cherry Studio 有完整生态。它能活下来只因为 Cherry Studio 不做 RP 叙事控制。
- **LM Studio 不在同一竞争维度**：LM Studio 卖的是"模型管理 + 本地推理运行时"，UI 只是附属。

## 5. 差异化与护城河

### 5.1 它凭什么活下来

| 护城河 | 说明 | 强度 |
| --- | --- | --- |
| **零部署即开即用** | 一个 HTML + 一个 .bat，无 Docker / 无 npm / 无编译。对"只想试试这个模型"的人是不可替代的 | 中高（但仅限 Windows；Mac/Linux 用户是它 issue 区的主要投诉来源） |
| **与自家模型的深度耦合** | 思维链级别、文风控制、状态栏都是"为 Tifa-Deepsex 量身定制"。Open WebUI 不会为一个小众 RP 模型做这些 | 中（护城河 = 模型本身，模型停更则壳失去意义） |
| **叙事参数控件化** | 把 RP 输出的文风/长度/节奏做成滑块——主流前端都还没有这个抽象层级 | 中高（**最可迁移、最值得抄**） |
| **状态栏 HUD** | 用近乎零成本的方式做出"角色状态可视化"的沉浸感 | 中（机制聪明但脆弱） |
| **在线版 leftnorth.com** | 无需本地 Ollama 直接可用，极低试用门槛 | 中 |

### 5.2 护城河的脆弱性

1. **无 License**：`license: null`，尽管上游是 Apache-2.0。任何人 fork/商用都有法律风险，也阻碍社区贡献。
2. **强绑定单一模型**：面板上写死"仅支持 UltraV2"。模型换代 → UI 失效。
3. **社区贡献未消化**：PR #3（模型名超长截断）、PR #10（修复导出）至今 open，说明维护带宽不足。
4. **配置体验是最大流失点**：11 个 issue 里 4 个（#5/#7/#8/#9）是"选不到模型 / 连不上 Ollama / 求 Mac 版"。**它把部署成本压到了零，却把配置成本留给了用户，且失败时无任何 UI 反馈**（fetch 失败只写 `console.error`）。

## 6. 产品短板（PRD 视角）

### 6.1 功能缺口

| 缺口 | 严重度 | 说明 |
| --- | --- | --- |
| **无角色卡** | 高 | 一个 RP 前端的及格线。已在自己更新计划里，未做 |
| **无世界书 / Lorebook** | 高 | RP 长期一致性的核心机制 |
| 无多模态 / 无语音 | 中 | 语音在计划中 |

### 6.2 工程质量问题（源码级观察）

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| **采样参数可能未生效** | `/api/chat` 请求体把 `temperature` / `top_p` / `repeat_penalty` / `max_output_tokens` 放在**顶层**；Ollama 的 chat 接口期望这些字段位于 `options` 内（`num_predict` 而非 `max_output_tokens`） | 用户调了参数没反应，**产品承诺与实际不符**。*（源码观察，待实测确认；不同 Ollama 版本行为可能不同）* |
| 流式解析脆弱 | 按 `}\n` 切分再 `JSON.parse`，出现跨 chunk 边界即抛错 | 对应 issue #2「Q8 模型输出解析错误」，且错误只打 console |
| 无错误提示 | 模型列表加载失败 `.catch(err => console.error(...))`，UI 无任何提示 | 直接导致 issue #5/#7/#9「选不到模型」 |
| 渲染性能 | 每收到一个 token 都 `chatContainer.innerHTML = ''` 后**全量重建**整个会话 DOM 并 `MathJax.typeset()` | 长会话明显卡顿 |
| 可维护性 | 2758 行单文件，CSS/JS/HTML 混杂，三处 `<style>` 分散，无模块、无类型、无测试 | 几乎无法协作开发 |
| CDN 强依赖 | MathJax / FontAwesome / 字体均走外网 CDN | 离线或 CDN 不可达时公式与图标失效 |
| XSS 面 | `messageDiv.innerHTML = content`（marked 解析结果），无 sanitize | 本地单机场景风险低，但在线版存在风险 |
| 无 License | — | 阻碍采用与贡献 |

## 7. 对「AI 酒馆」的借鉴清单

对照 AI 酒馆现状（Vue3+TS+Pinia，已有：角色卡/角色版本、世界书、群聊、故事引擎、DataBank RAG + 自定义 ONNX 向量模型、社区市场、扩展系统、自定义主题、本地模型(WebLLM)、Persona、随机事件、i18n 中英、Tauri 桌面端、Chat 的复制/重新生成/停止生成/导出 Markdown、ContextPanel 的 temperature+maxTokens）。

### 7.1 建议清单（按优先级）

| # | 建议 | 优先级 | 状态 | 理由与落地要点 |
| --- | --- | --- | --- | --- |
| 1 | **思维链（CoT）渲染 + 回传剥离**：`MessageBubble` 支持 `<think>…</think>` 折叠块（默认收起、可展开、显示思考耗时）；发送历史前剥离 assistant 的 think 内容 | **P0** | **我们缺** | 推理模型（Qwen3 / R1 系 / 各类 CoT 微调）已成主流，RP 场景中"看 AI 怎么想"本身也是乐趣。它把这个做成了第一优先级（0215 首个版本），验证了需求强度。要点：折叠态必须可持久化，且**不能回灌上下文** |
| 2 | **"思考强度"三档开关**：关/低/高，作为**可选**的提示词后缀注入（如"先用 <think> 简要推理，再回答"），仅对标记为"支持 CoT"的模型 profile 启用 | **P0** | **我们缺** | 极低成本的推理强度旋钮，绕开各家 API `reasoning_effort` 不统一的问题。要点：① 必须在设置里可见/可关；② 只在用户显式开启时注入；③ 用白名单避免对不支持的模型产生垃圾输出 |
| 3 | **叙事风格控制面板**：文笔风格 / 目标字数 / 旁白-对话占比 / 剧情节奏（段落密度），编译为**可预览、可编辑、可关闭**的提示词片段，作用域为"角色级 + 会话级" | **P1** | **我们缺**（ContextPanel 只有 temperature/maxTokens） | **这是它最值得抄的一点**。RP 用户的核心痛点正是"输出形态不受控"，而这些维度天然可控件化。我们要做得更好：编译结果对用户可见（它只 console.log）、可按角色/会话独立配置、提供"原始提示词"高级模式兜底 |
| 4 | **角色状态栏**：约定一个**显式协议**（而非正则猜测），把模型输出的状态块渲染为带图标的状态卡（地点/时间/在场角色/关系/想法），支持折叠与关闭 | **P1** | **我们缺** | 沉浸感强、记忆锚点清晰。但**不要抄它的正则猜格式**——那太脆。建议：约定 YAML/JSON front-matter 或明确的 ```` ```status ```` 围栏，配合世界书"状态条目"，并可关联到 DataBank/故事引擎的时间轴 |
| 5 | **补齐采样参数**：在 ContextPanel 增加 top_p、repeat_penalty（及 presence/frequency penalty）、输出到上下文的条数 | **P1** | **我们已有但不足** | 它给了 4 个，我们只有 2 个。RP 场景对重复惩罚尤其敏感（它 0301 专门"降低默认重复惩罚"）。要点：默认值需按"角色扮演"调优，而非照搬通用助手默认值 |
| 6 | **端点连接向导 / 自检**：新增 Ollama 等本地端点时，自动探测连通性、CORS、可用模型列表，并把失败原因（连不上 / CORS 被拦 / 无模型）**明确展示** | **P1** | **我们缺**（目前 dev 有 proxy，生产构建直连受阻） | 它的 issue 区 4/11 是"连不上/选不到模型"，且失败时零提示。这正是我们可以做成卖点的地方：README 已说明生产缺 proxy——把"告诉我为什么连不上"做成产品能力，比让用户读 README 强 |
| 7 | **生成期防误触升级**：生成中除禁用输入/按钮外，锁定"切换会话/切换角色/跳转路由"的导航，或二次确认 | **P1** | **我们已有基础**（`disabled` + `isGenerating` 守卫），可加强 | 它的做法（侧栏 `pointer-events:none`）提示了一个我们可能漏掉的场景：**生成中途切换会话会丢上下文**。建议加导航守卫 + `aria-busy`（我们已有 `aria-busy`） |
| 8 | **数学公式渲染**：引入 KaTeX（本地打包，非 CDN） | **P2** | **我们缺** | 理科向角色/教学人设有需求。约束：CI 有 CSP 守卫且禁止第三方字体 CDN，**必须 npm 本地打包 + 自托管字体**，不能用它那种 CDN 引法 |
| 9 | **代码块浮动/并排视图**：长代码块可弹出为可拖动浮层，主区自动让位 | **P2** | 我们已有代码块渲染，无浮动 | RP 场景优先级低（代码少），但对"AI 助手"向角色有用。它的"有代码时主区左移 10%"是低成本方案 |
| 10 | **导出格式补齐**：在现有 Markdown 导出外，增加 JSON（可回导）与纯文本 | **P2** | **我们已有且更优**（Markdown > 它的 txt），仅需补 JSON | 它的 localStorage 无法导入，数据迁移能力为零。我们已有 DataBank/档案体系，补一个可回导的 JSON 即可形成闭环 |

### 7.2 明确分类

**我们已有且更优（保持，不必羡慕）**
- 角色卡与角色版本管理、世界书（Lorebook）关键词门控、群聊与发言调度、故事引擎、DataBank + 自定义 ONNX 向量 RAG、社区市场（含哈希校验）、扩展系统（沙箱 + 按需权限）、自定义主题（k-means 取色）
- 多会话与档案（ArchivesView）体系、复制/重新生成/停止生成/导出 Markdown
- i18n（中英）+ i18n 严格门禁、CSP 守卫、CSS 约定守卫、覆盖率门禁、a11y 对比度门禁、Tauri 桌面端

**我们确实缺（值得补）**
- 思维链渲染与思考强度控制（#1、#2）——**最高优先级**
- 叙事风格参数化控制（#3）——**差异化机会**
- 角色状态栏（#4）
- 采样参数齐全度（#5）
- 本地端点连接自检与错误可视化（#6）
- 数学公式（#8）

**看似好但不适合我们（或不建议照抄）**
| 它的做法 | 为什么不照抄 |
| --- | --- |
| 单 HTML 文件即开即用 | 与我们的技术栈与 7 道 CI 门禁直接冲突。它的"零部署"优势换来的是不可维护、不可测试、不可协作。我们**不应该**追求分发形态上的极简 |
| 用提示词注入实现思考级别 | 脆弱（模型不听话即失效）。只能作"可选增强 + 明确标注"，不能当核心能力承诺 |
| 靠正则猜状态栏格式 | 模型格式一变就崩。我们要做就做**显式协议** |
| 无条件把风格配置追加到每条用户消息 | 用户失去控制权，且污染上下文。我们要可预览、可关、可按角色/会话作用域 |
| CDN 引 MathJax / FontAwesome / 字体 | 与我们的 CSP 守卫冲突，且离线不可用。必须本地打包 |
| 无 License | 反面教材。我们已有 LICENSE 与 THIRD_PARTY_NOTICES，继续保持 |

### 7.3 一句话总结

> 它是"**模型能力驱动**"的产品范本：UI 的每一次进化都对应模型的一次升级，因此能用 2758 行把一个 RP 模型的三类能力（推理、文风、状态）全部曝光给用户。
> 我们应当吸收的是它的**产品抽象**（思维链可视化、叙事参数控件化、角色状态 HUD），而明确拒绝它的**工程取舍**（单文件、CDN、无 License、无错误反馈）。
