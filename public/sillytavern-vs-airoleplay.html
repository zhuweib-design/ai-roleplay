01功能对比:核心模块逐一对照

功能模块SillyTavern本项目 ai-roleplay异同结论

桌面端 官方无(Node 服务器+浏览器;Android Termux 官方支持;社区 TauriTavern 1.2k stars) Tauri 2 一等公民,1280×800 原生窗口 + 最小权限 capabilities 本项目独有优势
故事创作 无 故事引擎全链:上传 → story-analyzer(3 档)→ world-generator/npc-generator/角色卡 → 导入,protagonist、story-time 时间推进 本项目独有,最核心差异化

服务器/多用户 支持(login.html + AccountStorage) 无 ST 胜
i18n 多语言 locales 无 ST 胜
结论

两者同源同目标(本地优先的角色扮演聊天),但分工不同——ST 是广度+生态,本项目是深度+现代工程。功能重叠度约 60%,本项目缺失的多为"生态类"(后端兼容面、多用户、i18n、STScript),独有的是"创作类"与"工程类"(故事引擎、版本控制、本地推理、安全基线、桌面原生)。

02优缺点分析

2.1 SillyTavern

✓ 优势

  • 生态即护城河:31.9k stars、300+ contributors、每月 release、官方内容库(SillyTavern-Content),扩展/角色卡/世界书资源海量。
  • 后端兼容面最广:所有主流 API + 本地后端 + 函数调用,几乎没有接不上的模型。
  • 社区标准制定者:角色卡 V2、STScript 成为事实标准,竞品只能兼容它。
  • 本地优先 + 多用户:数据落本地 data/,支持多用户登录。

✗ 劣势

  • 架构老化:无前端框架、无 TS 编译;index.html 717KB、script.js 483KB、style.css 144KB 手写维护;jQuery 重度 DOM 操作,长对话性能差、扩展互相干扰。
  • 安全模型原始:扩展"unrestricted access to the DOM and SillyTavern context",明文密钥,官方自己承认无法安全存密钥。
  • 无桌面端、无内置推理:体验依赖浏览器 + 用户自己搭外部后端,非技术用户上手门槛高。
  • 无创作工具链:只"聊",不"造"。

2.2 本项目 ai-roleplay

✓ 优势

  • 现代工程栈:Vue3 + TS + Pinia + Vite,类型安全;统一 alias、P0-P3 缺陷编号、覆盖率 80% 测试门禁、Playwright e2e。
  • 开箱即用的桌面 + 离线:Tauri 原生应用 + WebLLM 内置推理,装好就能聊,无需配服务器/API。
  • 安全设计领先:密钥加密、XSS 净化、SSRF 防护、最小权限 capabilities、严格 CSP。
  • 独特创作能力:故事引擎、角色版本控制、AI 生成角色/世界/NPC,是 ST 生态完全没有的增量。
  • 存储抽象干净:双后端(IndexedDB/Rust fs)同一接口,Web 可降级运行。

✗ 劣势

  • 生态为零:无社区、无扩展市场(当前是 mock)、无资源库,用户获取角色卡/世界书只能靠 ST 导入。
  • 后端兼容窄:仅 OpenAI 兼容;Anthropic 未实现,函数调用无(工具调用缺位)。
  • 扩展系统不安全实现:new Function 无沙箱,与 ST 同级的信任风险,却无 ST 的生态价值背书。
  • 本地推理不成熟:LocalApiClient 非真流式(一次性返回),WebGPU 性能/兼容性未验证,长对话下无虚拟滚动。
  • 半成品痕迹:单用户、无 i18n、市场 mock、PlaceholderView 死代码。
结论

ST 是"功能全但技术债重、安全裸奔";本项目是"工程好、体验好、安全好,但生态与兼容面空白"。两边劣势恰好是对方优势——这正是差异化路线图的依据。

03用户画像

维度描述
典型特征中文母语;非深度程序员但对 AI 感兴趣;愿意为"好用"折腾;注重数据隐私;喜欢写作与角色扮演
技术水位会用电脑、能装软件,但不会搭 llama.cpp/配 API 环境;属于 ST 生态"装不上、配不好"而流失的那批人
使用场景 ① 桌面离线聊角色(断网可用,web-llm)
② 小说/世界观创作者:写设定 → 生成角色与世界书 → 导入对话
③ 数据敏感者:API Key 本地加密、无服务器上传
④ 多模型对比党:本地 vs DeepSeek 等一键切换
核心需求装完即用、中文体验、数据不出本机、创作到对话一条龙、低成本(本地模型免费)
非目标用户深度 ST 玩家(生态依赖重)、需要多用户/共享服务的企业、英文市场
结论

本项目锚定的是 ST 生态的边缘人群 + 中文创作人群——ST 装不上/嫌麻烦的用户,以及"想造世界而不只是聊天"的作者。这个画像同时决定了:别跟 ST 拼生态广度,拼"更低门槛 + 更深的创作价值"。

04核心目标(按优先级)

优先级目标理由
P0-1 对话闭环体验达到 ST 同级:Anthropic 直连、工具调用、真流式本地推理、长对话虚拟滚动 这是产品的地基,地基不平,一切差异化无意义
P0-2 本地推理产品化:token 级流式、模型下载/缓存管理、WebGPU 降级 WASM、采样参数暴露 离线是本项目第一卖点,现在还是半成品
P0-3 数据安全闭环收尾:备份加密、导入导出审计、威胁模型文档 安全是第二卖点,且是"信任型"用户的下单理由
P1-1 故事引擎产品化:小说 → 可玩酒馆的一键流水线 + 模板库 唯一无法被 ST 复制的核心差异(可作护城河)
P1-2 扩展沙箱 v1:iframe/Worker 隔离 + 能力声明,替代裸 new Function 为 P1-3 铺路,且消除安全硬伤
P1-3 生态互通最大化:ST 角色卡/世界书/群聊/Quick Reply 全格式导入导出,兼容角色卡 V2 借 ST 生态的存量资源喂自己,成本远低于自建生态
P2-1 市场真实化(先模板/角色卡下载,后交易) 依赖 P1-3 的资源量
P2-2 i18n 英文 + 多用户/服务器模式 规模扩展期再上
结论

优先级逻辑 = 先补"与 ST 打平的基本盘"(P0)→ 再做"ST 抄不走的深度"(P1-1)→ 再借 ST 生态与自建生态扩张(P1-3/P2)。

05差异化优势与强化策略

本项目具备而 SillyTavern 不具备的五项能力:

优势 01

内置离线推理(web-llm)

ST 无任何内置推理,必须外接 llama.cpp/Kobold。

强化:token 级流式;模型下载/断点续传/磁盘缓存管理;自动 fallback(本地→远程);"离线包一键装";基准页(速度/token 数对比 DeepSeek)。
优势 02

桌面原生体验(Tauri 2)

ST 官方无桌面端,只有浏览器 + 社区移植。

强化:系统托盘 + 全局快捷键唤起;Tauri updater 自动更新;拖拽导入角色卡/世界书/PNG;断网检测提示;三端(Windows/macOS/Linux)安装包。
优势 03

故事创作工具链(独一无二)

小说上传 → 分析 → 世界生成 → NPC 生成 → 可玩,ST 完全没有。

强化:"10 分钟出可玩场景"流水线打磨;模板市场;世界书自动生成自检质量闭环。
优势 04

角色版本控制(git 式)

commit 链/分支/三方合并/回滚,ST 仅单版本。

强化:分支 diff 可视化、一键回滚、角色卡变更日志导出(分享"进化史");远期可选云同步。
优势 05

安全基线

密钥加密(AES-GCM + PBKDF2) + SSRF 防护 + 严格 CSP,ST 明文且自认无解。

强化:扩展升级为"权限声明 + 沙箱执行";安全白皮书作为营销资产;"数据导出审计日志"。
结论

五项优势中,故事工具链是最深护城河(ST 想抄要重构产品定位),离线+桌面是最好卖点,安全是信任背书。强化顺序:1、3 优先,2、5 随版本推进。

7.2 功能优先级原则

每迭代 60% 产能投 P0 稳定性、30% 投差异化、10% 技术债,杜绝只加新功能。

7.3 技术债务管理

  • 维持 P0-P3 缺陷编号注释机制,新债必编号;
  • CI 门禁(80% 覆盖率、typecheck、eslint)设为合入红线;
  • 每迭代末做一次"债清扫",清 10% 存量。

7.6 风险提示

最大路线风险:故事引擎质量达不到创作者预期(LLM 生成设定不稳定)。对策:v0.3 前用盲评样本集做质量回归——本项目文档 AI酒馆项目嵌入优化方案开发文档.md 已定义类似评估体系,可复用其指标框架(设定一致率、情绪保留率)。

总结

SillyTavern 是"生态之王但技术陈旧、安全裸奔";本项目应走"现代工程 + 低门槛离线 + 创作深度"的错位竞争路线——P0 补兼容与性能,用故事引擎做护城河,借 ST 存量生态做冷启动,半年内冲到 v1.0 可发布状态。

08后续计划:嵌入优化方案(待实现)

来源

本报告 v1.1 起纳入《AI酒馆项目嵌入优化方案开发文档.md》(v1.0)作为本项目后续待实现功能线。该方案为三层"中间件":不替换模型、不改用户交互,挂载在现有对话链路上,核心目标——设定长期稳定不被优化器覆盖、情绪连贯、压缩省 token。

8.1 三层架构总览

层模块核心职责状态
L0
上下文结构层		 MemoryStore / CharacterRegistry / EmotionTracker 版本化记忆(稳定 ID + 修订号 + 快照 + diff);字节稳定前缀组装(命中 DeepSeek 前缀缓存,价约 miss 的 1/10);会话级情绪状态机独立存储;standing 事实仅人工可写(硬约束防覆盖) 待实现
L1
内容压缩层		 CompressionPipeline / ExtractiveCompressor / SemanticValidator / CcrStore 提取式压缩(TextCrusher 思路,保留原句);语义校验(实体/情绪词保留率 ≥0.9,关键实体 1.0);CCR 无损端到端(24h TTL);豁免黑名单(standing/情绪/世界观永不压缩);三级回退(fail-open → 暂停 → /no-opt) 待实现
L2
输出纪律层		 OutputDiscipline 旁白分类(状态性旁白可精简,情绪/氛围旁白豁免);保护正则哨兵(对白/情绪词/设定实体硬豁免);Auto-Clarity 软回退(安全/不可逆/情绪冲突/重复提问时恢复完整表达) 待实现

可行性论证:三层均为增量改造、可灰度;收益可量化(前缀缓存每日对账、输出节省真实统计);风险可控(压缩默认关闭、fail-open、硬豁免 + 版本快照兜底)。

8.4 与本报告路线图的衔接

  • 落地形态待决策:方案文档假设 Python/FastAPI 服务端,而本项目当前为纯前端 + Tauri 无服务端——需在 v0.2 前定夺:内置 TS 实现(压缩/情绪/前缀在浏览器内完成,契合离线卖点)或新增 Node 服务端。
  • 与 P0/P1 并行:本方案是"对话质量与成本"工作线,与报告 P0(功能/体验补齐)、P1(故事引擎)并行推进,不互相阻塞。
  • 复用现有模块:情绪状态机可挂 variable-store.ts/会话状态;L1 压缩管线挂在 prompt-builder.ts 之后、LLM 调用之前(对现有链路只增不减);L0 版本化可直接沿用 character-version-control.ts 的修订/快照范式。
  • 指标框架互通:本方案的设定一致率/情绪保留率评估体系,与故事引擎质量回归(报告 7.6 风险对策)共用同一套盲评与抽取测试。
